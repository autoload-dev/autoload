# The "e2e as separate Bazel modules" pattern in Aspect / bazel-contrib rulesets

Scope: rules_js, rules_oci, rules_ts, rules_esbuild, rules_lint, bazel-lib (all Aspect-originated), bazel-contrib rules-template, rules_multitool, rules_bazel_integration_test, plus rules_python as the reference user of rules_bazel_integration_test. All findings are from files read on `main` on 2026-11-06 via the GitHub contents API / raw.githubusercontent.com unless noted. Nothing here is from blog posts; no Aspect blog post about e2e testing was found (see Gaps at the end).

## Key question 1: Layout — which directories are test-related, which are separate modules, what does the root `.bazelignore` contain?

### Takeaway
Every surveyed ruleset keeps three layers: Starlark unit/analysis tests and fixtures inside the main module (`js/private/test/`, `lib/tests/`, `oci/tests/`, `mylang/tests/`), one or more nested Bazel modules under `e2e/<name>/` (and often `examples/`) that consume the ruleset "from the outside", and a root `.bazelignore` that lists those nested module directories so the root module never tries to load them as packages.

### Inferences
- The naming is stable across the family: `e2e/<scenario>` = one consumer module per scenario; `examples/` = user-facing samples that double as integration tests (rules_js makes this explicit); `<lang>/private/test` or `<lang>/tests` = in-module tests that may load private `.bzl` files.
- rules_oci is the outlier that keeps most rule-level assertions in root-module `examples/*` packages (using a private `examples/assert.bzl`) rather than in `oci/private/test`; its `e2e/` is reserved for the consumer-view smoke module, the bats-driven `assertion` module, and a `wasm` scenario.
- `.bazelignore` listing the nested directories is the only mechanism these repos use to separate modules; none use `--deleted_packages` (that is the rules_bazel_integration_test approach, see question 7).

### Gaps
- Could not list rules_ts `docs/` module content (raw fetch of `docs/MODULE.bazel` returned 404 although `.bazelignore` lists `docs/` as a nested module); unclear whether it is still a module.

## Key question 2: Wiring — how do e2e workspaces reference the ruleset under test, and does any test against a released archive?

### Takeaway
Every e2e module declares `bazel_dep(name = "<ruleset>", version = "0.0.0" [, dev_dependency = True])` plus `local_path_override(module_name = "<ruleset>", path = "../..")`; no surveyed e2e module uses `archive_override` or a registry version of the ruleset under test. Released versions are used only for *other* rulesets the scenario needs (e.g. rules_ts 3.8.10 inside rules_js, rules_oci 2.3.0 inside rules_js).

### Inferences
- `version = "0.0.0"` is a sentinel; because the root `module()` of these rulesets leaves `version` unset, `local_path_override` always satisfies the dep regardless of the number.
- Marking the override as `dev_dependency = True` is a template convention (rules-template, rules_js, bazel-lib, rules_ts, rules_esbuild); rules_oci omits it. It has no practical effect since the e2e module is never consumed by anyone.
- Testing against a released archive of the *same* ruleset is intentionally not done in-repo; that job is delegated to the BCR presubmit (`bcr_test_module`, question 3), which re-runs `e2e/smoke` (or `e2e/bzlmod`) against the registry-published archive.
- Legacy `WORKSPACE` / `WORKSPACE.bzlmod` files in rules_oci and bazel-lib e2e dirs are residue of the dual-mode CI axis; rules_js and rules-template have dropped them (`--noenable_workspace` in rules_js's e2e.bazelrc).

### Gaps
- GitHub code search for `archive_override path:e2e org:aspect-build` hit the API rate limit, so "no e2e uses archive_override" is verified only for the e2e modules read individually (rules_js: bzlmod, js_image_oci, npm_translate_lock, git_dep_metadata, ts_version_from_rules_ts_3.8.10; rules_oci: smoke, assertion, wasm; bazel-lib: smoke, api_entries, copy_to_directory; rules_ts: smoke, external_dep; rules_esbuild: smoke; rules-template: smoke).

## Key question 3: CI — how are e2e folders run, on every PR, bazel_integration_test or plain shell? BCR presubmit?

### Takeaway
All of them run plain `bazel test //...` (or `aspect test ... -- //...`) with `working-directory: <folder>` inside a GitHub Actions matrix over `folder × bazelversion (× os × bzlmod)`, on every push/PR to main; an optional `test.sh` in the folder is executed afterwards for things Bazel cannot test from inside. None of the Aspect rulesets use rules_bazel_integration_test. The BCR presubmit re-runs one e2e module (`e2e/smoke` or `e2e/bzlmod`) as `bcr_test_module`.

### Cited Findings
- rules_js CI is `.github/workflows/ci-workflows.yaml` (no `ci.yaml`): triggers `push`/`pull_request` on `main`, `2.x`. Job `e2e-tests-list` builds the `workspace` axis as a bash array of 41 paths (`.`, 39 `e2e/*`, `examples`) and appends `e2e/git_dep_metadata`, `e2e/npm_translate_lock_git+ssh`, `e2e/pnpm_lockfiles` only if `ASPECT_GHTESTER_SSH_KEY` is set, and the three `npm_translate_lock_auth*` folders only if `ASPECT_NPM_AUTH_TOKEN` is set ("so PRs from forks skip them instead of failing") — [rules_js/.github/workflows/ci-workflows.yaml](https://github.com/aspect-build/rules_js/blob/main/.github/workflows/ci-workflows.yaml)
- rules_js job `test`: `runs-on: ubuntu-latest`, matrix `workspace × bazel` with bazel `7.x`, `8.x`, `9.x` (each with `--test_tag_filters=-skip-on-bazelN`), `timeout-minutes: 90`, step `aspect test $REMOTE_FLAG --task:name=test-<slug>-<bazel> <flags> -- //...` in `working-directory: ${{ matrix.workspace.path }}`, then "Optional ./test.sh": `if [[ -f ./test.sh ]]; then ./test.sh; else echo "No test.sh in ${PWD}; skipping"; fi`. A second job `test-variants` runs the same matrix with `bazel-9-no-execroot-entry-point`, `bazel-9-hermetic-launcher`, and `bazel-10` (`10.0.0rc1`) because "GitHub caps a single job matrix at 256 entries". Per-folder exclusions carry reasons (e.g. "e2e/js_image_oci pulls in the `llvm` module, whose hermetic toolchain requires Bazel 8+") — same file
- rules_js job `smoke` runs macOS/Windows only for `.` and `e2e/bzlmod`, only on `main` or branches containing `macos`/`windows` ("billed at 10X and 2X respectively"), with plain `bazel test --test_tag_filters=-skip-on-bazel7 //...` via `bazel-contrib/setup-bazel` — same file
- rules_js root-only extra steps: coverage smoke (`--collect_code_coverage` on `//js/private/test/coverage/...`, once per CI run) and "Check that unused npm packages were not fetched" (`ls $(bazel info output_base)/external | grep -vz unused`) — same file
- rules_js `e2e/js_binary_workspace/test.sh` is an example of a `test.sh`: it `bazel run`s `//:bazel_run_env` under both launcher flags with and without `BAZEL_BINDIR` set, as a regression for #3046 — [rules_js/e2e/js_binary_workspace/test.sh](https://github.com/aspect-build/rules_js/blob/main/e2e/js_binary_workspace/test.sh)

- Cost control is explicit and consistent: Linux on every PR, macOS/Windows only on `main` or specially named branches, matrix exclusions with comments.
- `test.sh` is the escape hatch for behaviour that needs `bazel run`/`bazel build` observed from outside (source-tree writes, env propagation, launcher regressions); it is run after `bazel test //...` in the same folder.

## Key question 4: What do e2e tests assert, and are helper libraries from the ruleset allowed?

### Takeaway
e2e modules assert at three levels: (a) `build_test` that public targets build, (b) running the ruleset's own test rules (`js_test`, `container_structure_test`, `bats_test`) against public outputs, and (c) golden/diff assertions on produced files using bazel-lib's public `diff_test`, `assert_contains`, `assert_json_matches`. They load only public entry points of the ruleset under test (`@aspect_rules_js//js:defs.bzl`, `@rules_oci//oci:defs.bzl`, `@bazel_lib//lib:*.bzl`); private `//lib/private` or `//js/private` loads appear only in root-module tests.

### Inferences
- The split is: in-module tests may load private `.bzl` and private helper macros; e2e modules load only what a consumer could (public `defs.bzl`, public extensions, public bazel-lib/skylib testing macros). This is enforced by Bazel itself: `//lib/private` or `//js/private` targets are not visible from another module unless exported.
- "What is asserted" scales with the ruleset: a template starts with a `build_test`; bazel-lib asserts outputs with `diff_test` against fixtures; rules_oci inspects produced artifacts with `jq`/`docker`; rules_js runs its own `js_test` rule as the assertion vehicle.
- Repository-rule failure modes (must-fail fetches) cannot be expressed as `bazel test` targets inside the same build, so rules_oci wraps a nested module in `bats_test` and shells out to `bazel build` — the only place in this family that runs Bazel-in-Bazel, and it is hand-rolled, not rules_bazel_integration_test.

### Gaps
- Not every e2e BUILD file was read (rules_js has 47 e2e dirs); the findings cover the representative ones named above.

## Key question 5: bazel-lib `lib/testing.bzl` — public API for consumers? How do rules_js/rules_oci use it?

### Takeaway
`lib/testing.bzl` is a public, documented entry point of bazel-lib (exported with `//visibility:public`, has its own `bzl_library`, is listed in the `e2e/api_entries` load test) providing `assert_contains`, `assert_outputs`, `assert_archive_contains`, `assert_directory_contains`; `assert_json_matches` lives in `lib/diff_test.bzl`-adjacent code and is loaded from `@aspect_bazel_lib//lib:testing.bzl` by rules_oci on the 2.x line. rules_js and rules_oci use them both in root-module tests and in e2e modules.

### Cited Findings
- `lib/testing.bzl` docstring "Helpers for making test assertions"; defines `assert_contains(name, actual, expected, size="small", **kwargs)` ("Generates a test target which fails if the file doesn't contain the string. ## Key question 7: rules_bazel_integration_test — what it does, how it compares to plain e2e folders, maintainer-stated pros/cons

### Takeaway
rules_bazel_integration_test turns a child workspace into a `bazel test` target that downloads one or more Bazel binaries (`bazel_binaries` extension; versions from `.bazelversion`, explicit, `last_green`, or `self`) and runs a test runner (`default_test_runner` = `bazel info` + `bazel test //...`, or a custom script) inside that workspace; it requires `--deleted_packages` bookkeeping instead of `.bazelignore`. None of the Aspect rulesets use it; rules_python does, and its maintainers document the costs (heavy, uncapped parallelism, symlink-globbing hazards, nested-Bazel debugging) and have moved tests out of it where possible.

### Cited Findings
- README: "This repository contains Bazel macros that execute integration tests that use Bazel (e.g. execute tests in a child workspace). The macros support running integration tests with multiple versions of Bazel." Setup: `bazel_dep(name = "rules_bazel_integration_test", version = "0.37.1", dev_dependency = True)`; `bazel_binaries = use_extension("@rules_bazel_integration_test//:extensions.bzl", "bazel_binaries", dev_dependency = True)`; `bazel_binaries.download(version_file = "//:.bazelversion")`, `.download(version = "6.0.0")`, `.download(version = "last_green")` — [rules_bazel_integration_test README](https://github.com/bazel-contrib/rules_bazel_integration_test/blob/main/README.md)
- README step 3: "If you have child workspaces under your parent workspace, you need to tell Bazel to ignore the child workspaces... 1. Add entries to the `.bazelignore` file... 2. Specify a list of deleted packages using the `--deleted_packages` flag. For `glob()` in the parent workspace to find files in the child workspaces, we need to use the deleted packages mechanism." Populated by `bazel run @rules_bazel_integration_test//tools:update_deleted_packages` — same

- Third-party summary (VirtusLab "Bazel book" §4.5.2 "Ruleset Integration Tests"): integration tests "check whether a downstream-style workspace can load a ruleset, declare real BUILD targets, run Bazel, and get the promised behavior"; pros: "Tests the path users actually follow", "Fixtures double as examples"; cons: "Costly: each fixture may start a separate Bazel server", and for the plain examples-folder approach "Bazel isn't run under its test runner, the version may not be pinned, and local state can leak in"; recommends "Keep local presubmit narrow... Move broad version and platform matrices to release or scheduled CI", "Keep one behavior per fixture" — [bazel.virtuslab.com/book/4~5~2](https://bazel.virtuslab.com/book/4~5~2/) (secondary source; summarised by the fetch tool, not verified verbatim)

### Inferences
- Trade-off as practised: plain e2e folders push the matrix into CI (one job per folder × Bazel version, parallel on cheap Linux runners, `bazel test //...` semantics identical to what a user runs, `.bazelignore` only); rules_bazel_integration_test pulls the matrix into one Bazel invocation (good when CI job slots are the constraint, as rules_python states) at the price of nested Bazel servers, `--deleted_packages` maintenance, `manual` tags/test_suites, and harder debugging.
- The Aspect family's answer to "test against several Bazel versions" is the CI matrix plus `USE_BAZEL_VERSION`/`.bazelversion` rewrite, not in-Bazel version downloads.
- Bazel-in-Bazel remains necessary for negative repository-rule tests; both rules_oci (bats) and rules_python (BIT) reserve it for "anything that happens prior to the analysis phase".

### Gaps
- No Aspect maintainer statement explicitly rejecting rules_bazel_integration_test was found; the absence in all Aspect repos is observed, not explained by them.
- Searches for an Aspect blog post about e2e/ruleset testing ("Aspect blog testing Bazel rulesets e2e smoke test", "blog.aspect.build bazel ruleset e2e tests local_path_override") returned no such post; the only Aspect blog reference found in these repos is https://blog.aspect.build/releasing-bazel-rulesets-rust (about shipping prebuilt tool binaries), cited in the rules-template README.

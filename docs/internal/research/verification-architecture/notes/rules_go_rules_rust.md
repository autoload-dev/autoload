# Test architecture of rules_go and rules_rust

Evidence basis: shallow clones of `bazel-contrib/rules_go` (commit `f9689452`, 2026-10-29, default branch `master`) and `bazelbuild/rules_rust` (commit `d08ddace`, 2026-11-06, default branch `main`), read directly; plus the Tweag article on testing Bazel rules (secondary). All paths below are repository-relative; URLs point at the default branch.

## Key question 1: Directory layout (unit/analysis tests, integration tests, examples; separate modules; CI)

### Takeaway
rules_go keeps everything under one `tests/` tree inside the root module (`tests/core`, `tests/integration`, `tests/legacy`, `tests/examples`, `tests/extras`, `tests/runfiles`), with two nested consumer modules (`tests/bcr`, `examples/basic_gazelle`) that are run by CI via `working_directory`. rules_rust keeps in-module tests under `test/` (`test/unit` for analysis/unit tests, everything else as end-to-end targets) and runs a large number of nested, separate Bazel modules (`test/integration/*`, `examples/*`, `crate_universe/tests/integration/*`, `extensions/*`) one CI task each, every one wired by `local_path_override` to the repo root.

### Inferences
- Both rulesets rely on BazelCI `working_directory` tasks, not on a Bazel rule, to test nested consumer modules; neither uses `rules_bazel_integration_test`. The nested-module pattern is cheap to author (plain directories) but means `bazel test //...` from the root does not cover them, and every new nested module needs a presubmit entry.
- rules_rust's "unit" naming refers to Starlark `analysistest`/`unittest` tests of rule behaviour, not to Rust-level unit tests; "integration" means a separate module. rules_go's "core" vs "integration" split is by scope (single feature vs real-world repos), with the integration mechanism (`go_bazel_test`) used in both.
- rules_go's `examples/basic_gazelle` pins a released version rather than overriding to the checkout, so it tests the consumer experience against the BCR, not the working tree; rules_rust's examples always override to the working tree.

### Gaps
- No written rationale was found for why rules_rust splits `test/` from `examples/` beyond the ARCHITECTURE.md sentence; no README in `examples/` or `crate_universe/test`.

## Key question 2: Integration-test mechanism (rules_go `go_bazel_test`/`bazel_testing`; rules_rust equivalent)

### Takeaway
rules_go's `go_bazel_test` is a `go_test` wrapper whose Go runtime (`bazel_testing.TestMain`) copies/links the ruleset's `//:all_files` filegroup into a fixed directory under the output user root as `tested_repo`, extracts a txtar `Main` archive into `main/`, synthesises a `MODULE.bazel` with `bazel_dep` + `local_path_override` to `tested_repo` (exposing the host Go SDK via a `new_local_repository` wrap), then runs the real `bazel` from `PATH`; tests are tagged `local` + `exclusive`. rules_rust has no such harness: its integration tests are nested modules run by CI tasks, plus Rust-level subprocess tests for `cargo-bazel`.

### Cited Findings
- `go_bazel_test(rule_files = None, **kwargs)` docstring: "go_bazel_test is a wrapper for go_test that simplifies the use of //go/tools/bazel_testing. Tests may be written that don't explicitly depend on bazel_testing or rules_go files." Defaults `rule_files = [Label("//:all_files")]`, appends `@io_bazel_rules_go//go/tools/bazel_testing` to `deps`, adds `rule_files` to `data` and `-begin_files $(rlocationpaths ...) -end_files` to `args`, sets `rundir = "."`, and adds tags `local` ("don't run in sandbox or on remote executor") and `exclusive` ("run one test at a time, since they share a Bazel output directory. If we don't do this, tests must extract the bazel installation and start with a fresh cache every time, making them much slower.") — [go/tools/bazel_testing/def.bzl](https://github.com/bazel-contrib/rules_go/blob/master/go/tools/bazel_testing/def.bzl).
- `//:all_files` is a `testonly = True` filegroup in the root `BUILD.bazel` listing `BUILD.bazel`, `MODULE.bazel`, `WORKSPACE`, `go.mod`, `go.sum` and `//extras:all_files`, `//go:all_files`, `//proto:all_files`, `//third_party:all_files`; each package defines its own `testonly` `all_files` filegroup (`glob(["**"])` + subpackages), e.g. `go/BUILD.bazel`, `go/private/BUILD.bazel`, `go/tools/BUILD.bazel`, `go/tools/bazel_testing/BUILD.bazel` — [BUILD.bazel](https://github.com/bazel-contrib/rules_go/blob/master/BUILD.bazel), [go/BUILD.bazel](https://github.com/bazel-contrib/rules_go/blob/master/go/BUILD.bazel).
- Package doc of `bazel_testing.go`: "Package bazel_testing provides an integration testing framework for testing rules_go with Bazel. Tests may be written by declaring a go_bazel_test target instead of a go_test (go_bazel_test is defined in def.bzl here), then calling TestMain. Tests are run in a synthetic test workspace. Tests may run bazel commands with RunBazel." `Args` fields: `Main` (txtar archive; "If this archive does not contain a MODULE.bazel file, a default file will be synthesized."), `Nogo`, `NogoIncludes`, `NogoExcludes`, `ModuleFileSuffix`, `SkipHostGoSDK`, `SetUp func() error` — [go/tools/bazel_testing/bazel_testing.go](https://github.com/bazel-contrib/rules_go/blob/master/go/tools/bazel_testing/bazel_testing.go).
- `setupWorkspace` in the same file: locates the output base from `TEST_TMPDIR` (`.../execroot/` prefix) and uses `<outBase>/bazel_testing/bazel_go_test` as a fixed `execDir`, writing `startup --output_user_root=<parent of output base>` so the child Bazel shares the parent's user root; copies or links every runfile from `rule_files` into `execDir/tested_repo` (rejecting files from more than one repo); reads the module name from `tested_repo/MODULE.bazel` (and the repo name from `WORKSPACE` if present); writes `main/.bazelrc` with `common --enable_bzlmod` and `common $GO_BAZEL_TEST_BAZELFLAGS`; extracts `Args.Main` into `main/`; if no `MODULE.bazel` is present, renders `defaultModuleBazelTpl`.
- `defaultModuleBazelTpl` content: `bazel_dep(name = "{{.TestedModuleName}}", repo_name = "{{.TestedModuleRepoName}}")` + `local_path_override(module_name = ..., path = "{{.TestedModulePath}}")`; "Provided by default so that fixtures don't have to declare them themselves": `platforms` and `rules_cc`; `cc_configure_extension` → `local_config_cc`; a `new_local_repository(name = "local_go_sdk", path = "{{.GoSDKPath}}")` and `go_sdk.wrap(root_file = "@local_go_sdk//:ROOT")` exposed as `@go_sdk` ("which is the name fixtures refer to it by"); optional nogo block adding `gazelle` + `golang.org/x/tools`; then `{{.Suffix}}` — same file.
- The host SDK path comes from `x_defs = {"goRootFile": "$(rlocationpath {})".format(HOST_COMPATIBLE_SDK)}` on the `bazel_testing` `go_library`, whose `data` includes `HOST_COMPATIBLE_SDK` files — [go/tools/bazel_testing/BUILD.bazel](https://github.com/bazel-contrib/rules_go/blob/master/go/tools/bazel_testing/BUILD.bazel).
- Fixture code loads the public API by apparent repo name: `load("@io_bazel_rules_go//go:def.bzl", "go_library", "nogo", "TOOLS_NOGO")` inside the txtar (e.g. `tests/core/nogo/bzlmod/includes_excludes_test.go`, `tests/core/go_binary/package_conflict_test.go`) — [tests/core/nogo/bzlmod/includes_excludes_test.go](https://github.com/bazel-contrib/rules_go/blob/master/tests/core/nogo/bzlmod/includes_excludes_test.go).
- `.bazelrc`: "Improve caching, but allow integration tests to find `bazel` in PATH." (`--incompatible_strict_action_env` on macOS/Linux + `common --test_env=PATH`); `test:incompatible --test_env=GO_BAZEL_TEST_BAZELFLAGS='...'` "Also enable all incompatible flags in go_bazel_test by default." — [.bazelrc](https://github.com/bazel-contrib/rules_go/blob/master/.bazelrc).
- Usage count: 42 `BUILD.bazel` files declare `go_bazel_test(` (tests/core/* incl. 20 nogo subdirs, tests/integration/{cgo_ldflags,gazelle,go_bin_runner,reproducibility}, tests/legacy/{examples/stamped_bin,no_prefix}, tests/runfiles, and `go/tools/gopackagesdriver` with `size = "enormous"`). `tests/core/go_test/BUILD.bazel` mixes 9 `go_bazel_test` with 26 plain `go_test` — clone grep; [go/tools/gopackagesdriver/BUILD.bazel](https://github.com/bazel-contrib/rules_go/blob/master/go/tools/gopackagesdriver/BUILD.bazel).
- `tests/core/go_bazel_test/` tests the macro itself ("Tests that `data` and `args` provided to `go_bazel_test` are provided to the go test framework correctly.") — [tests/core/go_bazel_test/README.rst](https://github.com/bazel-contrib/rules_go/blob/master/tests/core/go_bazel_test/README.rst).
- Tweag (2022, secondary): "consists of a Starlark macro and a Go library with some helper functions to set up a test workspace"; the fixed directory "weakens hermeticity"; "it makes it impossible to run such tests in parallel, so they have to use the `exclusive` tag"; contrasts `rules_bazel_integration_test` (plain nested workspace dirs, `BIT_BAZEL_BINARY`/`BIT_WORKSPACE_DIR`, multiple Bazel versions) and criticises the `examples/` approach of rules_rust/rules_nixpkgs as "non-hermetic, non-reproducible, and inconvenient" — [Tweag: Bazel rules to test Bazel rules](https://www.tweag.io/blog/2022-10-06-bazel-rules-to-test-bazel-rules/). (The article predates bzlmod; the `local_repository`/`WorkspaceSuffix` details it describes are now `local_path_override`/`ModuleFileSuffix`.)
- rules_rust: grep for `bazel_integration_test` / `rules_bazel_integration_test` in the clone returns nothing; the only in-process integration harness is `crate_universe`'s `cargo_integration_test` (`rust_test` with `CARGO`/`RUSTC` env from `$(rlocationpath ...)`, `timeout = "long"`), which skips itself when `github.com:443` is unreachable — [crate_universe/tests/cargo_integration_test.rs](https://github.com/bazelbuild/rules_rust/blob/main/crate_universe/tests/cargo_integration_test.rs).
- rules_rust `test/integration/bzlmod_repo_mapping` is a three-module chain (A → B → C, B renames C via `repo_name`) checking runfiles `rlocation!` through repo mappings; CI runs it from `module_a` — [test/integration/bzlmod_repo_mapping/README.md](https://github.com/bazelbuild/rules_rust/blob/main/test/integration/bzlmod_repo_mapping/README.md).

### Inferences
- The child workspace sees exactly what `//:all_files` ships — the full source tree including `go/private` — but fixtures reference the public `@io_bazel_rules_go//go:def.bzl` API because they are consumer modules; nothing technically prevents a fixture from loading `//go/private`. The "public API only" property is by convention, not enforced.
- Sharing the parent's `output_user_root` and a fixed exec dir is what makes 42+ Bazel-in-Bazel tests affordable; the price is `local` + `exclusive` and host-tool dependence (`bazel` on `PATH`).
- rules_rust avoids Bazel-in-Bazel entirely, pushing the cost to CI task count (~60 `working_directory` tasks) instead of test runtime.

### Gaps
- No design doc or issue discussing why rules_go chose this harness over `rules_bazel_integration_test` was found; the only rationale is in code comments (`def.bzl` tag comments) and the Tweag article.

## Key question 3: Analysis tests (framework, location, loading private `.bzl`)

### Takeaway
Both rulesets use `@bazel_skylib//lib:unittest.bzl` (`unittest` for pure functions, `analysistest` for rule behaviour) in a dedicated tests tree, not beside the implementation; rules_rust additionally adopted `@rules_testing` for a handful of newer tests. Both load private `.bzl` files directly from the tests tree (rules_go: 6 loads of `//go/private:*`; rules_rust: ~15 loads of `//rust/private:*`, marked `# buildifier: disable=bzl-visibility`).

### Cited Findings
- rules_go `tests/core/starlark/`: `common_tests.bzl`, `context_tests.bzl`, `module_info_tests.bzl`, `provider_tests.bzl`, `sdk_tests.bzl` (each exporting a `*_test_suite()` called from `BUILD.bazel`), plus `cgo/cgo_test.bzl` and `packagedriver/go_pkg_info_aspect_test.bzl`. `common_tests.bzl` loads `@bazel_skylib//lib:unittest.bzl` (`asserts`, `unittest`) and `//go/private:common.bzl` (`count_group_matches`, `has_shared_lib_extension`). README: "Checks that `has_shared_lib_extension` from `//go/private:common.bzl` correctly matches shared library filenames" — [tests/core/starlark/common_tests.bzl](https://github.com/bazel-contrib/rules_go/blob/master/tests/core/starlark/common_tests.bzl), [tests/core/starlark/README.rst](https://github.com/bazel-contrib/rules_go/blob/master/tests/core/starlark/README.rst).

## Key question 4: Test support packages (helpers, visibility, documentation)

### Takeaway
rules_go's `//go/tools/bazel_testing` (Go library + `def.bzl` `bzl_library`) is `//visibility:public` and importable as `github.com/bazelbuild/rules_go/go/tools/bazel_testing` (pkg.go.dev indexes it), but it is not mentioned in any rules_go `.rst`/`.md` documentation outside `tests/`; its txtar dependency is `//go/tools/internal/txtar` with visibility `//go/tools:__subpackages__`. rules_rust's helpers are `test/unit/common.bzl` (`package(default_visibility = public)`, `exports_files`) and per-test-dir `*_test_utils.bzl`; nothing in `rust/private` is marked test-only.

## Key question 5: Testing that consumers use only public API; visibility, `bzl_library`, `testonly` conventions

### Takeaway
Neither ruleset has an automated check that fixtures use only public API. The closest mechanisms are: nested consumer modules that load only `@rules_go//go:def.bzl` / `@rules_rust//rust:defs.bzl` (rules_go `tests/bcr` with a renamed `repo_name = "my_rules_go"`, rules_rust `examples/*`), rules_go's `bzl_library` visibility (`//go/private:*` libraries visible only to `//go:__subpackages__`, `//docs`, `//extras`), and rules_rust's ARCHITECTURE.md policy. `testonly` is used systematically only in rules_go (`all_files` filegroups and the Go test-support `all_files`), never in `rules_rust/rust/`.

### Cited Findings
- rules_go `tests/bcr/MODULE.bazel` declares `bazel_dep(name = "rules_go", version = "", repo_name = "my_rules_go")` and the BUILD loads `@my_rules_go//go:def.bzl`, `@my_rules_go//extras:gomock.bzl`; `other_module` loads `@rules_go//go:extensions.bzl` — i.e. the consumer module is exercised under a non-default apparent repo name — [tests/bcr/BUILD.bazel](https://github.com/bazel-contrib/rules_go/blob/master/tests/bcr/BUILD.bazel), [tests/bcr/other_module/MODULE.bazel](https://github.com/bazel-contrib/rules_go/blob/master/tests/bcr/other_module/MODULE.bazel).
- rules_go `go/private/BUILD.bazel`: `bzl_library` targets `context` (visibility `//docs:__subpackages__`, `//extras:__pkg__` "Manually added", `//go:__subpackages__`), `go_toolchain`, `repositories`, `sdk`, `common` (`//go:__subpackages__`); `config_setting`s `stamp`, `is_strip_*` are `//:__pkg__`; but the `all_rules`/`all_files` filegroups are public — [go/private/BUILD.bazel](https://github.com/bazel-contrib/rules_go/blob/master/go/private/BUILD.bazel).
- rules_go `go/BUILD.bazel`: public `bzl_library(name = "def")` depends on `//go/private:*` libraries; `filegroup(name = "all_files", testonly = True, ...)` and `filegroup(name = "all_rules", srcs = glob(["*.bzl"]) + ...)` (not testonly) — [go/BUILD.bazel](https://github.com/bazel-contrib/rules_go/blob/master/go/BUILD.bazel).
- rules_go `testonly` occurrences in `go/` (grep): `go/BUILD.bazel`, `go/tools/BUILD.bazel`, `go/tools/{coverdata,builders,bazel_testing,bzltestutil,bzltestutil/chdir,go_bin_runner,bazel}/BUILD.bazel` — all `all_files` filegroups (and two builder targets).
- rules_go `.bazelrc` `build:incompatible` enables `--incompatible_config_setting_private_default_visibility`, `--incompatible_enforce_config_setting_visibility`, `--incompatible_disallow_empty_glob`, etc., run in the `ubuntu2404` CI task with `--config=incompatible`, and forwards the same flags into child workspaces via `GO_BAZEL_TEST_BAZELFLAGS` — [.bazelrc](https://github.com/bazel-contrib/rules_go/blob/master/.bazelrc), [.bazelci/presubmit.yml](https://github.com/bazel-contrib/rules_go/blob/master/.bazelci/presubmit.yml).
- rules_rust `ARCHITECTURE.md`: "`//rust:defs.bzl` is the file that all users of `rules_rust` will be using. Everything in this file can be used (depended on) and is supported ... Also other packages in `rules_rust` should access core rules through the public API only. We expect dogfooding our own APIs increases their quality." and "Depending on `//rust/private` from packages other than `//rust` is not supported, we reserve the right to change anything there and not tell anybody." — [ARCHITECTURE.md](https://github.com/bazelbuild/rules_rust/blob/main/ARCHITECTURE.md).
- rules_rust `rust/private/BUILD.bazel`: single `bzl_library(name = "bzl_lib", srcs = glob(["**/*.bzl"]), visibility = ["//rust:__subpackages__"])`; `rust/BUILD.bazel` has `package(default_visibility = public)`, `exports_files(["defs.bzl", "toolchain.bzl"])`, and a public `bzl_lib` — [rust/private/BUILD.bazel](https://github.com/bazelbuild/rules_rust/blob/main/rust/private/BUILD.bazel), [rust/BUILD.bazel](https://github.com/bazelbuild/rules_rust/blob/main/rust/BUILD.bazel).

- rules_rust unit tests load the public API for targets under test (`load("//rust:defs.bzl", "rust_binary", "rust_library", ...)`) and private modules only for helper functions — [test/unit/crate_name/crate_name_test.bzl](https://github.com/bazelbuild/rules_rust/blob/main/test/unit/crate_name/crate_name_test.bzl).
- rules_rust CI mutates the root module to simulate consumer configurations (`sed` injecting `versions = [...]` into `rust.toolchain(` for min-Rust / stable-only / nightly-only tasks) — [.bazelci/presubmit.yml](https://github.com/bazelbuild/rules_rust/blob/main/.bazelci/presubmit.yml).

### Inferences
- "Consumer uses only public API" is verified empirically through the nested modules (a load of `//rust/private` or `//go/private` from a nested module would still work, since those files are in the overridden module), so it is a review convention, not a build-time guarantee, in both projects.
- rules_go's `bzl_library` visibility restricts Stardoc/`bzl_library` dependency graphs, not `load()` statements; it is the only place where "private" is encoded as Bazel visibility.

### Gaps
- No lint or CI check enforcing `bzl-visibility` in either repo was found (buildifier runs in rules_go via `//tests:buildifier_test`, but whether it enables the `bzl-visibility` warning was not verified).

## Key question 6: Explicit maintainer statements about why the layout is the way it is

### Takeaway
rules_go documents its test rules in `tests/README.rst` (documented per-folder READMEs, one responsibility per test, always on in CI, no flakes, all platforms, fast — external deps belong in integration tests). rules_rust's only architectural statement is `ARCHITECTURE.md` (examples demonstrate, `//test` tests; `//rust/private` unsupported) and `CONTRIBUTING.md` ("A PR should contain tests for the change where feasible.").

### Cited Findings
- rules_go `tests/README.rst` "Adding a new test": "They must be documented — Each test folder must contain a README.rst that documents the area of reponsability for the folder. That README must have a section with the same name as each of the test rules that documents exactly what the test is supposed to be checking for. If the test is in response to a previous issue, the documentation must also link to the issue being addressed." / "Test one thing at a time ... Prefer writing multiple tests in a single folder to a single test that excercises multiple things." / "They must be turned on — Test that do not run by default on the CI machines are not much use" / "They must not be flakey — We will generally just delete tests that flake, and if features cannot be tested without flakes we will probably delete the feature as well." / "They must work on all platforms — We support mac, linux and windows" / "They must be as fast as possible ... downloading large external dependancies to perform a small unit test is not ok, prefer creating a small local replication of the problem instead. Anything that requires external dependancies beyond those of the rules belongs in the integration tests." — [tests/README.rst](https://github.com/bazel-contrib/rules_go/blob/master/tests/README.rst).
- rules_go per-folder README example: `tests/core/cgo/README.rst` starts with issue anchors (`.. _#2067: https://github.com/bazelbuild/rules_go/issues/2067`) and has one section per test target describing what it checks — [tests/core/cgo/README.rst](https://github.com/bazel-contrib/rules_go/blob/master/tests/core/cgo/README.rst).
- rules_go root `MODULE.bazel` comments explain dev-only wiring: "The maintainer tools under go/tools are separate Go modules so that their dependencies don't end up in //:go.mod, which is also used to pick the Go SDK version."; "Only used by //tests/legacy/examples/external ... It isn't imported by //:go.mod, which doesn't cover the separate Go module under tests/."; "Used to transition binaries in rules_go's test suite to different configurations." (`with_cfg.bzl`); "For testing the compatibility with a hermetic cc toolchain. Users should not have to enable it." — [MODULE.bazel](https://github.com/bazel-contrib/rules_go/blob/master/MODULE.bazel).
- rules_go root `BUILD.bazel` comment on why no root `gazelle` target: "It can't go here though, because it would break anything that depends on rules_go but not Gazelle, including our own go_bazel_tests." — [BUILD.bazel](https://github.com/bazel-contrib/rules_go/blob/master/BUILD.bazel).
- rules_rust `ARCHITECTURE.md`: "In general we try to follow the common standard defined by https://docs.bazel.build/versions/master/skylark/deploying.html." plus the `//rust`, `//rust/private`, `//examples`, `//test` sections quoted above — [ARCHITECTURE.md](https://github.com/bazelbuild/rules_rust/blob/main/ARCHITECTURE.md).
- rules_rust `CONTRIBUTING.md`: "A PR should contain tests for the change where feasible."; also states core-rule scope, that non-core rules will be split into separate repositories, and that Windows / other platforms are best-effort ("Platforms other than Linux / MacOS / Windows: Best effort maintenance, no CI testing.") — [CONTRIBUTING.md](https://github.com/bazelbuild/rules_rust/blob/main/CONTRIBUTING.md).
- rules_rust `docs/src/index.md`: "We do not have sufficient maintainer expertise to support Windows. Most things probably work, but we have had to disable many tests in CI because we lack the expertise to fix them." — [docs/src/index.md](https://github.com/bazelbuild/rules_rust/blob/main/docs/src/index.md).

### Inferences
- rules_go's test policy is the more transferable artefact: README-per-folder with a section per test target, generated cross-links (`update.py`), explicit "external deps only in integration" rule, and a nested BCR module as the canonical consumer test.
- rules_rust's extension split (`extensions/*` as independent BCR modules with their own `test/` trees) is the current maintainers' stated direction for non-core functionality and is mirrored in CI as per-module `working_directory` tasks.

### Gaps
- No GitHub issue or design doc was located that discusses the test layout decisions themselves (searches for a design discussion returned only pkg.go.dev mirrors and the Tweag article); `tests/README.rst` is the only first-party rationale.

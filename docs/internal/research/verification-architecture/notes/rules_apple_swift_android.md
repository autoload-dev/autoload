# Test architecture of rules_apple, rules_swift and rules_android

Scope: where tests live, which kinds exist, which helper packages they use, whether
helpers are public, how examples are wired, and whether white-box and consumer-view
tests are separated. State as of the `main` branches on 2026-11-05/06 (rules_apple
pushed 2026-11-05, rules_swift 2026-11-05, rules_android 2026-11-06), read directly
from the repository trees via the GitHub API. All three are Bzlmod modules; only
rules_android still ships WORKSPACE files (flagged below).

## rules_apple: layout of `test/`, artifact verification, examples, consumer-facing testing infra

### Takeaway
rules_apple keeps all ruleset tests inside the main module under `test/`, split into
(a) Starlark analysis tests and bundle-verification tests under `test/starlark_tests/`
(the bulk, ~380 files) and (b) a handful of shell integration tests `test/*.sh` that
spin up a scratch Bzlmod workspace with `local_path_override` on rules_apple. The
verification rule `apple_verification_test` is explicitly declared an implementation
detail ("Please do not depend on this rule"), while `apple/testing/default_runner/` is
the public, consumer-facing test-runner infrastructure for `ios_unit_test` etc.

**How artifact verification works (`apple_verification_test`)**
- `apple_verification_test.bzl` docstring: "Test rule to perform generic bundle verification tests. This rule is meant to be used only for rules_apple tests and are considered implementation details that may change at any time. Please do not depend on this rule." It loads `//apple/internal:apple_product_type.bzl` with `# buildifier: disable=bzl-visibility` — [apple_verification_test.bzl](https://github.com/bazelbuild/rules_apple/blob/main/test/starlark_tests/rules/apple_verification_test.bzl)
- Mechanism: a Starlark `transition` (`apple_verification_transition`) on `target_under_test` sets `//command_line_option:platforms` to `@apple_support//platforms:darwin_x86_64`, `compilation_mode`, `ios_multi_cpus`/`tvos_cpus`/`watchos_cpus`/`visionos_cpus` depending on `build_type` (`simulator` or `device`), optional `cpus` dict, `features`/`sanitizer`, and build settings (defaults `signing_certificate_name = "-"`). The rule impl reads `AppleBundleInfo` (archive, `bundle_name + bundle_extension`, `Payload/<bundle>` for ios/tvos app archives, `Contents/MacOS/<exe>` for macOS) or `AppleBinaryInfo`, expands the template `//test/starlark_tests:verifier_scripts/apple_verification_test_runner.sh.template` with `%{archive}s`, `%{archive_relative_binary}s`, `%{archive_relative_bundle}s`, `%{archive_relative_contents}s`, `%{archive_relative_resources}s`, `%{verifier_script}s`, `%{dependencies}s`, sets `BUILD_TYPE`, `XCODE_VERSION_MAJOR/MINOR` and `APPLE_TEST_ENV_*` env vars (string lists transformed into bash arrays) and returns `DefaultInfo(executable = script, runfiles = [archive, verifier_script, _test_deps])` plus the target's `OutputGroupInfo`. The verifier script sees env `ARCHIVE_ROOT`, `BINARY`, `BUILD_TYPE`, `BUNDLE_ROOT`, `CONTENT_ROOT`, `RESOURCE_ROOT` — [apple_verification_test.bzl](https://github.com/bazelbuild/rules_apple/blob/main/test/starlark_tests/rules/apple_verification_test.bzl)
- Attributes: `apple_generate_dsym`, `build_settings` (string_dict), `build_type` (mandatory, `simulator`/`device`), `compilation_mode`, `cpus` (string_list_dict), `objc_enable_binary_stripping`, `objc_generate_linkmap`, `sanitizer` (`none|asan|tsan|ubsan`), `target_features`, `target_under_test` (providers `[[AppleBinaryInfo], [AppleBundleInfo]]`, `cfg = apple_verification_transition`), `verifier_script` (`.sh`), `env`; private `_runner_script`, `_test_deps = "//test:apple_verification_test_deps"`, `_xcode_config` — [apple_verification_test.bzl](https://github.com/bazelbuild/rules_apple/blob/main/test/starlark_tests/rules/apple_verification_test.bzl)
- `//test:apple_verification_test_deps` is a `testonly` filegroup of `apple_shell_testutils.sh` and `unittest.bash`, with the comment "This is required as a default attribute of apple_verification_test but should be considered private for other uses" and `visibility = ["//visibility:public"]` — [test/BUILD](https://github.com/bazelbuild/rules_apple/blob/main/test/BUILD)
- Verifier scripts (14): `app_clip_codesign_verifier.sh`, `app_clip_entitlements_verifier.sh`, `app_intents_metadata_json_sorted.sh`, `apple_symbols_file_verifier.sh`, `apple_verification_test_runner.sh.template`, `archive_contents_test.sh`, `binary_contents_test.sh`, `codesign_verifier.sh`, `codesignopts_verifier.sh`, `entitlements_verifier.sh`, `entry_point_verifier.sh`, `no_custom_fmwks_verifier.sh`, `order_file_verifier.sh`, `versioned_framework_verifier.sh` — [verifier_scripts tree](https://github.com/bazelbuild/rules_apple/tree/main/test/starlark_tests/verifier_scripts)
- `common_verification_tests.bzl` wraps the rule in macros; `archive_contents_test(name, build_type, target_under_test, contains, not_contains, is_binary_plist, is_not_binary_plist, plist_test_file, plist_test_values, asset_catalog_test_file, asset_catalog_test_contains, ..., text_test_file, text_test_values, binary_test_file, binary_test_architecture, binary_contains_symbols, binary_not_contains_architectures, codesign_info_contains, macho_load_commands_contain, assert_directory_file_count, assert_file_permissions, **kwargs)` converts the lists into `env` arrays for `archive_contents_test.sh`; paths may reference `$BUNDLE_ROOT`, `$CONTENT_ROOT`, `$RESOURCE_ROOT`, `$ARCHIVE_ROOT`, `$BINARY` — [common_verification_tests.bzl](https://github.com/bazelbuild/rules_apple/blob/main/test/starlark_tests/rules/common_verification_tests.bzl)
- `archive_contents_test.sh` iterates `CONTAINS[@]` with `eval echo "$path"` and `[[ -e ]]` checks, greps `TEXT_TEST_FILE` with POSIX BRE regexes, checks `lipo -archs` against `BINARY_NOT_CONTAINS_ARCHITECTURES`, and fails via `fail` from `unittest.bash`; the archive was already unzipped by the runner template into `ARCHIVE_ROOT` — [archive_contents_test.sh](https://github.com/bazelbuild/rules_apple/blob/main/test/starlark_tests/verifier_scripts/archive_contents_test.sh)

### Inferences
- rules_apple's "white-box" tests (Starlark analysis + verification) load private `//apple/internal` packages directly and are visibility-restricted to `//test:__subpackages__`; the "consumer-view" tests are the shell integration tests that write a scratch `MODULE.bazel` with `local_path_override` and load `@rules_apple//...` labels. Both live in the same module; the separation is by mechanism (scratch workspace), not by a second checked-in module.
- Because the shell integration tests are `skipci`-tagged and `size = "large"`, CI coverage relies almost entirely on the Starlark verification tests and `examples/...` build tests; the shell tests are run manually by maintainers.
- The verification pattern "transition the target under test → unzip the archive in a runner script → run a verifier shell script with env-provided expectations" is the direct analogue of what a Godot ruleset would need for `.ipa`/`.apk`/`.app`/PCK inspection.
- Where a helper target must be public for mechanical reasons (default attribute of a rule, runfiles of generated workspaces), rules_apple makes it `//visibility:public` but documents "do not depend on this" in a comment rather than modelling a separate API surface.

### Gaps
- No maintainer document explains why Starlark verification tests replaced most shell tests; `test/README.md` and `CONTRIBUTING.md` are silent. Git history would be needed for the rationale (not researched).
- I did not read every `*_tests.bzl` file; counts of individual test targets per rule were not computed.

- rules_swift has no scratch-workspace shell integration layer like rules_apple's `bazel_testrunner.sh`; its only consumer-view test is the external layering-check module, which exists because the feature under test (layering check across module boundaries) requires an external repo, not as a general policy.

## rules_android: `test/` layout, examples as separate modules, Android-specific tooling tests (manifest merge, resources, APK inspection), helper visibility

### Takeaway

### Inferences
- rules_android is the only one of the three with a formal in-tree "consumer module" pattern: examples are independent modules that depend on the ruleset by name with `local_path_override`, excluded from the root module by `.bazelignore`, and built by CI from their own `working_directory`. This gives a cheap, honest consumer-view build without a second checkout.
- Its scratch-workspace integration tests (`rules_bazel_integration_test` `script_test` + bashunit) are heavier and partly `manual` (e.g. `r8_desugaring_integration_test`, `demo_test`), so routine CI coverage comes from analysis tests, `py_test` APK inspection and the example builds.
- White-box tests freely load internal implementation (`//rules:resources.bzl` `resources.process`), and the "public" `PROJECT_VISIBILITY` at the `.bzl` level is a repo-wide default rather than an intent to expose `test/utils` to consumers; BUILD-level visibility is what restricts it to `//test/...`.

### Gaps
- No README under `test/` and no design document on the test layout exists in rules_android; the only statements are the inline comments in `examples/basicapp/MODULE.bazel`, `README.md` and `.bazelci/presubmit.yml`.
- I did not inspect `src/` Java/Go unit tests of the busybox/tools (they are tool tests, outside the ruleset-test scope); counts above exclude them.

## Cross-cutting: white-box vs consumer-view separation, module strategy, fixture ownership, rationale

### Takeaway
None of the three rulesets maintains a dedicated "consumer tests" module alongside the
main one. All keep white-box tests in the main module under `test/`, loading private
`internal` packages as needed and restricting helper visibility to `//test/...`.
Consumer-view coverage is achieved by (a) in-module examples built in CI (rules_apple,
rules_swift), (b) examples as separate modules with `local_path_override` (rules_android),
or (c) scratch workspaces generated at test runtime with `local_path_override`
(rules_apple shell tests, rules_android `script_test`s). Fixtures are owned by the tests
(per-topic packages tagged `manual`), never shipped as a consumer-facing fixture API.

### Cited Findings
- rules_apple: helper `bzl_library` `visibility = ["//test:__subpackages__"]` and deps on `//apple/internal:*` — [test/starlark_tests/rules/BUILD](https://github.com/bazelbuild/rules_apple/blob/main/test/starlark_tests/rules/BUILD); scratch module `rules_apple_integration_tests` with `local_path_override` — [test/bazel_testrunner.sh](https://github.com/bazelbuild/rules_apple/blob/main/test/bazel_testrunner.sh); examples load `//apple:ios.bzl` in-module — [examples/ios/HelloWorld/BUILD](https://github.com/bazelbuild/rules_apple/blob/main/examples/ios/HelloWorld/BUILD)
- rules_swift: `package(default_visibility = ["//test:__subpackages__"])` in `test/rules/BUILD` and `test/fixtures/BUILD`; `swift_shell_test.bzl` loads `//swift/internal:toolchain_utils.bzl` — [test/rules/BUILD](https://github.com/bazelbuild/rules_swift/blob/main/test/rules/BUILD); [swift_shell_test.bzl](https://github.com/bazelbuild/rules_swift/blob/main/test/rules/swift_shell_test.bzl); separate external module only for layering-check — [MODULE.bazel](https://github.com/bazelbuild/rules_swift/blob/main/MODULE.bazel)
- rules_android: `.bazelignore` = `examples`; `examples/basicapp/MODULE.bazel` `local_path_override(path = "../../")`; CI `working_directory: examples/basicapp` — [.bazelignore](https://github.com/bazelbuild/rules_android/blob/main/.bazelignore); [examples/basicapp/MODULE.bazel](https://github.com/bazelbuild/rules_android/blob/main/examples/basicapp/MODULE.bazel); [.bazelci/presubmit.yml](https://github.com/bazelbuild/rules_android/blob/main/.bazelci/presubmit.yml)

- "Public but please do not depend on it" pattern: rules_apple `//test:apple_verification_test_deps` ("should be considered private for other uses"), `//test/testdata/rules` ("Public only because these are used by the integration tests from generated workspaces"), `apple/testing/default_runner` targets ("should be considered an implementation detail of the rules") — [test/BUILD](https://github.com/bazelbuild/rules_apple/blob/main/test/BUILD); [test/testdata/rules/BUILD](https://github.com/bazelbuild/rules_apple/blob/main/test/testdata/rules/BUILD); [apple/testing/default_runner/BUILD](https://github.com/bazelbuild/rules_apple/blob/main/apple/testing/default_runner/BUILD)
- Shared bash test harness: rules_apple vendors `test/unittest.bash` and `apple_shell_testutils.sh`; rules_android vendors `test/bashunit/unittest.bash` + `unittest_utils.sh` as `sh_library` — [rules_apple test/BUILD](https://github.com/bazelbuild/rules_apple/blob/main/test/BUILD); [rules_android test/bashunit/BUILD](https://github.com/bazelbuild/rules_android/blob/main/test/bashunit/BUILD)
- Dev-dependency hygiene: rules_swift marks toolchains, Android/Kotlin/Java deps, stardoc, gazelle, python as `dev_dependency = True`; rules_android marks `stardoc`, `rules_bazel_integration_test`, `cgrindel_bazel_starlib`, `bazel_binaries` as dev; rules_apple marks only `stardoc` as dev — [rules_swift MODULE.bazel](https://github.com/bazelbuild/rules_swift/blob/main/MODULE.bazel); [rules_android MODULE.bazel](https://github.com/bazelbuild/rules_android/blob/main/MODULE.bazel); [rules_apple MODULE.bazel](https://github.com/bazelbuild/rules_apple/blob/main/MODULE.bazel)

### Inferences
- The three projects converge on "one module, `test/` for white-box, examples for consumer smoke coverage"; the choice between in-module examples and separate-module examples correlates with whether the ruleset's own root module would otherwise need the example's heavy dependencies (rules_android's examples need Maven/SDK setup the ruleset root already has, yet they still chose separate modules to make the example MODULE.bazel copy-pasteable for users).
- Artifact verification tests in all three are a thin test rule (transition + runfiles + env) over a script that unzips the bundle/APK and uses platform tools (`lipo`, `codesign`, `PlistBuddy`, `aapt2`, `dexdump`, `zipper`, `llvm-readelf`); expectations are passed as attributes and turned into env vars or script args.

### Gaps
- No explicit maintainer statement in any of the three repos explains the white-box/consumer-view split or the module strategy; everything above is inferred from BUILD files, CI configs and inline comments.

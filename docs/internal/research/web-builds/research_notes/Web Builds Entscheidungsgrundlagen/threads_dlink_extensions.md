## 1. How `variant/thread_support` and `variant/extensions_support` select the template, and what else they change

### Takeaway
The two boolean export options map 1:1 onto the template file name (`web[_dlink][_nothreads]_{debug,release}.zip`) and additionally drive feature tags, the HTML `$GODOT_THREADS_ENABLED` constant (which gates the browser feature check for cross-origin isolation), the PWA service worker's on-demand cache list (`.side.wasm` + extension `.wasm` files only when extensions are on), and the visibility of the `threads/*` pool-size options. `gdextensionLibs` in `GODOT_CONFIG` is filled from the shared objects the pack export collects, **regardless** of `extensions_support`; a mismatch is only caught at runtime in JS.

### Inferences
- The prototype's `godot_web_application` must replicate: (1) template choice, (2) `$GODOT_THREADS_ENABLED`, (3) `gdextensionLibs` + copying extension `.wasm` files, (4) `.side.wasm` in the PWA opt-cache when dlink — all keyed on the same two booleans. The pack export's feature tags must use the same booleans, otherwise `.gdextension` resolution (threads vs nothreads library) and `OS.has_feature` diverge from the runtime.
- Because Godot only fails at page load when extensions are packed into a non-dlink export, a ruleset can add a build-time check that Godot itself lacks (extensions present ⇒ dlink required).

### Gaps
- Not checked whether `custom_html_shell` users commonly drop `$GODOT_THREADS_ENABLED`; behavior for custom shells depends on the shell.

## 2. What `dlink` means technically, its cost, and ABI constraints for extensions

### Takeaway
`dlink` templates are Emscripten dynamic-linking builds: a tiny `MAIN_MODULE=1` runtime (`godot.wasm`, ~1.5 MB, `EXPORT_ALL`) that load-time-links all of Godot as a side module (`godot.side.wasm`, ~44 MB) plus the extensions' side modules. Cost in 4.7.2: about +15 % uncompressed wasm, +13 % zipped, a 10× larger `godot.js` (2.86 MB vs 0.28 MB), and Emscripten's documented dynamic-linking runtime overhead. Extensions must be built as side modules with matching threads setting (`-sUSE_PTHREADS`/`-pthread` or not), `WASM_BIGINT`, `SUPPORT_LONGJMP=wasm`, and in practice the same Emscripten version as the template, since Emscripten has no stable ABI between versions.

### Cited Findings

- Main module: libraries reset, `SIDE_MODULE=2` removed, `-s MAIN_MODULE=1`, `-s EXPORT_ALL=1`, `-s WARN_ON_UNDEFINED_SYMBOLS=0`, built only from `web_runtime.cpp`; all Godot code linked into `godot.side${PROGSUFFIX}.wasm` — [$G47/platform/web/SCsub:79-99]($G47/platform/web/SCsub); template ZIP gets `godot.side.wasm` as third file — [$G47/platform/web/emscripten_helpers.py:33-51]($G47/platform/web/emscripten_helpers.py)

- Upstream regression evidence of version sensitivity: Emscripten 6.0.1 broke dlink+threads, fixed in 6.0.12; Godot 4.8 now hard-fails dlink+threads builds below 6.0.12 — [$G48/platform/web/detect.py:116-122]($G48/platform/web/detect.py); [godotengine/godot#124321](https://github.com/godotengine/godot/pull/124321)
- Godot docs (4.7): "The default export templates do not include GDExtension support for performance and compatibility reasons." — [Compiling for the Web (stable/4.7)](https://docs.godotengine.org/en/stable/engine_details/development/compiling/compiling_for_web.html)

### Inferences
- Extension libraries for web are a **per-(threads) ABI** artifact: a threads side module (shared memory, atomics) cannot be loaded into a nothreads main module and vice versa; the ecosystem convention (godot-cpp suffix `.nothreads`, `.gdextension` keys `web.*.threads.wasm32` vs `web.*.wasm32`) treats threads as a library-selection dimension, like CPU.
- The dlink dimension does **not** change the extension's ABI (extensions are always side modules), only whether the template can load them. So for extension libraries, threads is ABI-relevant, dlink is not.
- Emscripten version is a third ABI dimension that is fixed per Godot minor release (see question 3); the ruleset could pin it in `profiles.bzl` per Godot version.
- The ~4.6 MB larger uncompressed download and 2.6 MB larger JS are a real cost; making dlink opt-in or derived (only when needed) matches Godot's own default.

### Gaps
- No published runtime-performance numbers for dlink vs static templates were found (only Emscripten's qualitative "can add overhead").
- No official Godot/godot-cpp statement found that the extension's Emscripten version must exactly equal the template's; evidence is community reports plus upstream regressions. Whether a minor-version difference (e.g. 4.0.20 vs 4.0.23) works was not tested.

## 3. Emscripten version used by official 4.7.x / 4.8 builds, and stability

### Takeaway
Official Godot 4.7.2 web templates are built with **Emscripten 4.0.20** (verified from the shipped `godot.js`), which is the pinned version in the `4.7` branch of `godotengine/build-containers` (same as 4.6). Godot 4.8 beta1 uses **Emscripten 6.0.12** and requires ≥ 6.0.1 (≥ 6.0.12 for dlink+threads). The version is pinned per release branch of the build containers and has historically changed only between minor releases, not patch releases; CI uses a different version (4.0.11) than releases.

- A ruleset can pin the extension Emscripten version per Godot minor version (4.7 → 4.0.20, 4.8 → 6.0.12) in the engine profile. ## 4. Threads on the web: requirements, browser support, Godot's workaround, known problems, hosts

### Takeaway
Threaded exports need `SharedArrayBuffer`, i.e. a secure context **and** cross-origin isolation (COOP `same-origin` + COEP `require-corp`, or `credentialless`). Godot 4.3 restored single-threaded export and the docs now call it "the preferred and now default way" because isolation is hard to configure, blocks third-party content (ads/monetization), and caused macOS/iOS problems. Godot can fake the headers with its PWA service worker. Static hosts without header control (GitHub Pages) need the service worker; itch.io has an opt-in SharedArrayBuffer embed option based on `credentialless`, which Safari does not support.

### Cited Findings
- MDN: "To use shared memory your document must be in a secure context and cross-origin isolated"; the constructor is hidden unless the headers are set; check via `crossOriginIsolated`; available across browsers since December 2021 — [MDN SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)
- Godot docs (4.7 stable): single-threaded export is "the preferred and now default way to export your games on the Web"; it is more compatible with itch.io, Poki, CrazyGames and works well on macOS/iOS; threads give better performance and low-latency audio with Stream playback; threads require HTTPS/localhost and COOP `same-origin` + COEP `require-corp`, which means the site "can't include ads or third-party integrations"; PWA + "Enable Cross Origin Isolation Headers" simulates the headers via service worker; without headers or workaround "the project will not run" — [Exporting for the Web (stable = 4.7)](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- The same docs page claims Extensions Support "also requires the cross-origin isolation headers" — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); **contradicted** by the 4.7.2 source, which ships `web_dlink_nothreads_*` templates and gates the isolation check only on threads ([$G47/platform/web/js/engine/features.js:94-101]($G47/platform/web/js/engine/features.js), [$G47/platform/web/export/export_plugin.h:59-73]($G47/platform/web/export/export_plugin.h)). The docs sentence likely dates from 4.2 when dlink templates were threads-only.
- Godot blog "Web export in 4.3" (2024): "we bet on the wrong horse" with SharedArrayBuffer; "we underestimated the difficulty of configuring cross-origin isolated websites"; isolation means "Adieu game monetization"; itch.io's option relies on `coep:credentialless`, unsupported by Safari and Firefox for Android; macOS/iOS issues "fortunately disappear" single-threaded; single-threaded audio garbled on low-end/high-FPS machines, fixed by reintroducing sample playback (`audio/general/default_playback_type` = Sample on web, experimental) — [Progress report: Web export in 4.3](https://godotengine.org/article/progress-report-web-export-in-4-3/) (describes 4.3; still the background for 4.7)
- Godot service worker `ensureCrossOriginIsolationHeaders(response)` rewrites responses with COEP `require-corp` and COOP `same-origin` — [$G47/misc/dist/html/service-worker.js:40-60, 79, 127, 138]($G47/misc/dist/html/service-worker.js); it is only registered when PWA is enabled (`config.serviceWorker` set only under `progressive_web_app/enabled`) — [$G47/platform/web/export/export_plugin.cpp:164-167 (serviceWorker at 166)]($G47/platform/web/export/export_plugin.cpp)
- Godot docs: Godot 4 C# projects cannot be exported to the web; only Compatibility renderer (WebGL 2); Safari has WebGL 2 issues, Chromium/Firefox recommended; GitHub Pages compresses on the fly; serve `.wasm` as `application/wasm` — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- COEP `credentialless` support (caniuse, 2026): Chrome ≥ 96, Firefox ≥ 119; **not** supported in Safari desktop up to 27.3, Safari iOS up to 27.2, Firefox Android 160 — [caniuse: COEP credentialless](https://caniuse.com/mdn-http_headers_cross-origin-embedder-policy_credentialless)
- itch.io: opt-in "SharedArrayBuffer support" checkbox under Embed Options → Frame Options; serves the game from a separate CDN domain with COOP `same-origin` on HTML, COEP `require-corp` on files and `credentialless` on the game page; Firefox support came via an origin trial; a user claims the origin-trial token expired end of 2023 (unconfirmed) — [itch.io: SharedArrayBuffer enabled](https://itch.io/t/2025776/sharedarraybuffer-enabled), [itch.io blog: Godot, cross-origin isolation and SharedArrayBuffers](https://itch.io/blog/456223/godot-cross-origin-isolation-and-sharedarraybuffers) (forum/admin posts, dated)
- GitHub Pages does not allow custom response headers; the open request is [GitHub community discussion #13309](https://github.com/orgs/community/discussions/13309); the common workaround is a header-injecting service worker like [coi-serviceworker](https://npmjs.org/package/coi-serviceworker); meta tags cannot set COOP/COEP ([WICG discussion](https://discourse.wicg.io/t/question-self-isolateorigin-ability-for-a-page-or-origin-to-programmatically-self-isolate/5787))
- CrazyGames: a Godot 4.4 user reports CrazyGames QA flagged "SharedArrayBuffer unsupported" with a custom template; works with the stock nothreads template — [Godot forum: issues exporting to CrazyGames](https://forum.godotengine.org/t/has-anyone-else-had-issues-exporting-to-crazygames/110385) (anecdotal)
- `threads/godot_pool_size` must be below `threads/emscripten_pool_size` "otherwise deadlocks may occur"; some browsers cap thread counts — [$G47/platform/web/doc_classes/EditorExportPlatformWeb.xml:81-88]($G47/platform/web/doc_classes/EditorExportPlatformWeb.xml)

### Inferences
- For a ruleset, threads is primarily a **hosting/deployment** property (headers or service worker, no third-party embeds) plus an ABI property for extensions. A `bazel run` server already sends COOP/COEP, so local runs work for both; deployment targets differ.
- If threads is chosen, the PWA service worker becomes effectively mandatory for hosts without header control, so threads and the PWA decision (prototype decision 5) are coupled.
- Safari/iOS users on itch.io's credentialless mode cannot run threaded builds; this strengthens "no threads" as default.

### Gaps
- No primary statement from Poki, CrazyGames or Newgrounds on COOP/COEP header support was found; the Godot docs only say nothreads is "more compatible" with Poki/CrazyGames. Newgrounds: no source found.
- No current (2026) primary source on Safari-specific threaded-build bugs beyond the 2024 blog's general statement.

## 5. GDExtension without threads (`dlink_nothreads`) in 4.7, and other limitations

### Takeaway
Yes: 4.7.2 ships and selects `web_dlink_nothreads_{debug,release}.zip`, and extensions load via the same `dynamicLibraries` path with no isolation requirement; the extension must be a nothreads side module. C#/.NET web export is unsupported in Godot 4 (hard error in the exporter).

### Cited Findings
- The official template set contains `web_dlink_nothreads_{debug,release}.zip` with `godot.wasm` + `godot.side.wasm` — local `unzip -l $T47/web_dlink_nothreads_release.zip`; built by `"target=template_release dlink_enabled=yes threads=no"` — [godot-build-scripts build-web/build.sh](https://github.com/godotengine/godot-build-scripts/blob/main/build-web/build.sh)
- `dlink` + `threads=no` is a valid SCons combination in 4.7.2 (the only constraints are `proxy_to_pthread` off); 4.8 adds an Emscripten ≥ 6.0.12 gate only for dlink **with** threads — [$G47/platform/web/detect.py:286-301]($G47/platform/web/detect.py), [$G48/platform/web/detect.py:120-122]($G48/platform/web/detect.py)
- The isolation feature check is skipped unless `threads` is requested — [$G47/platform/web/js/engine/features.js:94-101]($G47/platform/web/js/engine/features.js)
- A forum answer recommends selecting the stock `dlink_nothreads` template for a third-party extension shipping a wasm build, which then worked — [Godot forum: GDExtension not loading in web export](https://forum.godotengine.org/t/gdextension-not-loading-in-web-export/81867) (anecdotal)
- C#: `has_valid_export_configuration` under `MODULE_MONO_ENABLED` returns the error "Exporting to Web is currently not supported in Godot 4 when using C#/.NET. Use Godot 3 …" — [$G47/platform/web/export/export_plugin.cpp:425-431]($G47/platform/web/export/export_plugin.cpp)
- Extensions in a side module compiled with `EM_ASM`/`EM_JS` need `eval`; Godot's `javascript_eval` defaults to on — [Emscripten: Dynamic Linking](https://emscripten.org/docs/compiling/Dynamic-Linking.html); [$G47/platform/web/detect.py:54, 268-269]($G47/platform/web/detect.py)

### Inferences
- The ruleset's own add-ons (sqlite, app_auth, platform_paths, dart in `$RG/examples`/`addons`) need a nothreads web build at minimum; threads builds would double the extension matrix.
- Godot's runtime refuses a pack with extensions in a non-dlink template, so "dlink iff the pack has extensions" (option D) is the only working pairing in one direction; the other direction (dlink without extensions) works but wastes ~1.3 MB zipped.

### Gaps
- Not verified by running a nothreads side module in the 4.7.2 `dlink_nothreads` template (no local experiment done).

## 6. How comparable Bazel rulesets model such a dimension, and trade-offs of options (a)–(d)

### Takeaway
Comparable rulesets split: emsdk models threads as a **per-binary attribute** that transitions the whole dependency graph via a toolchain *feature* (`use_pthreads`), not as a platform constraint; apple_support/rules_apple model device vs simulator as a **platform constraint** (`target_environment`). rules_godot already uses the constraint style for the iOS environment and a `string_flag` + toolchain `target_settings` for debug/release, so both mechanisms are available for threads/dlink.

### Cited Findings
- emsdk `wasm_cc_binary` attribute `threads` ∈ {`_default`, `emscripten`, `off`}; its incoming-edge transition on `cc_target` appends `use_pthreads` / `-use_pthreads` to `--features`, sets `--platforms=@emsdk//:platform_wasm`, `--dynamic_mode=off`, `--cpu=wasm` — [emsdk bazel/emscripten_toolchain/wasm_cc_binary.bzl:4-40, 70-100](https://github.com/emscripten-core/emsdk/blob/main/bazel/emscripten_toolchain/wasm_cc_binary.bzl)
- emsdk toolchain: feature `use_pthreads` adds `-pthread` to all compile and link actions; `supports_dynamic_linker` is disabled; `-shared` on dynamic-library link actions — [emsdk bazel/emscripten_toolchain/toolchain.bzl:325, 424, 560-565, 763-769](https://github.com/emscripten-core/emsdk/blob/main/bazel/emscripten_toolchain/toolchain.bzl)
- emsdk platform `platform_wasm` = `@platforms//cpu:wasm32` + `@platforms//os:emscripten` (no threads constraint) — [emsdk bazel/BUILD:5-11](https://github.com/emscripten-core/emsdk/blob/main/bazel/BUILD)
- emsdk Bazel is bzlmod-only; Emscripten version defaults to the emsdk module version and can be overridden with `emscripten_deps.config(version = …)`; the default cache lacks LTO, 64-bit and **PIC** system libraries, which must be configured via `emscripten_cache` — [emsdk bazel/README.md](https://github.com/emscripten-core/emsdk/blob/main/bazel/README.md)
- apple_support: `constraint_setting(name = "target_environment", default_constraint_value = ":device")` with values `device`, `simulator`, `catalyst` — [apple_support constraints/BUILD](https://github.com/bazelbuild/apple_support/blob/main/constraints/BUILD)
- rules_godot: `godot_export_platform(environment = "device"|"simulator")` for iOS maps to `@apple_support//constraints:{device,simulator}` — [$RG/godot/platforms/BUILD.bazel:71-90, 125-133]($RG/godot/platforms/BUILD.bazel); constraints are owned by `godot_export_platform` ("Operating system, CPU and iOS environment constraints are owned by godot_export_platform") — [$RG/godot/private/config/settings.bzl:404-405]($RG/godot/private/config/settings.bzl)
- rules_godot: `//godot:variant` is a `string_flag` (`debug|editor|release`) that "selects debug runtimes and source-built extension libraries" — [$RG/godot/BUILD.bazel:44-56]($RG/godot/BUILD.bazel); runtime toolchains combine platform constraints (`target_compatible_with`) with `target_settings = [_VARIANT_SETTINGS[variant], engine_setting]` — [$RG/godot/engine/private/components.bzl:338-346]($RG/godot/engine/private/components.bzl)
- The prototype web platform is `godot_export_platform(name = "web_wasm32", cpus = ["@platforms//cpu:wasm32"], operating_system = "web")` with no threads/extensions attribute — [$RG/godot/platforms/BUILD.bazel:92-97]($RG/godot/platforms/BUILD.bazel)
- Prototype decision table (A fixed, B platform attribute/constraint, C build setting, D derived) and recommendation "B for threads, D or B for dlink" — [$RG/docs/internal/web-prototype.md:38-55]($RG/docs/internal/web-prototype.md)
- rules_rust: no wasm/emscripten threads constraint found in `rust/platform/BUILD.bazel` (search returned nothing) — [rules_rust rust/platform](https://github.com/bazelbuild/rules_rust/tree/main/rust/platform) (absence, low confidence)

### Inferences
Trade-offs per option, grounded in the findings above:

- **(a) Fixed: nothreads; dlink only when needed.** Matches Godot's default (both options default `false`) and the docs' recommendation. Extension builds need only one web ABI (nothreads side module). Loses threads entirely; users needing threads would need a custom template path. Cheapest for caching (one runtime slice per variant). The "dlink only when needed" half is really option (d) or (b) for dlink.
- **(b) Platform attribute/constraint (like iOS `environment`).** Threads changes native ABI of extension libraries (`-pthread`/`USE_PTHREADS`, `THREADS_ENABLED`, `.nothreads` suffix) exactly like simulator vs device changes ABI on iOS, so a constraint lets `cc` toolchain resolution, `select()` and `target_compatible_with` see it (e.g. an add-on can be incompatible with threaded web). Each extra value is a separate platform (`web_wasm32`, `web_wasm32_threads`, …) and a separate configuration → no cache sharing between them, but that is unavoidable for ABI-differing native code. Emscripten C++ toolchains could be registered per constraint (`-pthread` feature) instead of emsdk's per-binary transition. For dlink, a constraint is less fitting: dlink does not change extension ABI, only the runtime choice and the shell.
- **(c) Build setting (like `//godot:variant`).** Mechanically feasible: rules_godot already routes `variant` into runtime toolchain resolution through `target_settings`, and the same pattern would select `web` vs `web_nothreads` runtimes. But a flag is global per build: one invocation cannot build both a threads and nothreads web app, and native extension compilation must read the same flag (via a feature or `select`), which emsdk does by transition rather than by flag. A flag is also invisible to `@platforms`-based compatibility, so incompatible add-ons are not skipped automatically. Fits dlink better than threads, since dlink is a packaging/runtime choice.
- **(d) Derived from the pack's contents.** Godot itself never derives it (the exporter copies shared objects regardless and only the browser rejects them), so deriving it would add safety Godot lacks. The extensions are known at analysis time in Bazel (they are deps of the pack), so the decision could be made in the application rule without runtime toolchain resolution depending on file content — but then the runtime toolchain must offer both dlink and non-dlink templates and the application rule picks among them, i.e. the runtime "executable" becomes a pair. Cannot apply to threads, which is a user choice about hosting.
- A combination suggested by the evidence: threads as platform attribute/constraint (ABI + hosting, matching emsdk's distinction at the binary level and apple_support's at the platform level), dlink derived from whether the pack has web extension libraries (no ABI impact on extensions, size cost only when needed), with an error if extensions are present but dlink is disabled explicitly.

### Gaps
- No Bazel ruleset was found that models a Godot-like "dynamic-linking-capable runtime" dimension; rules_rust wasm modeling not investigated in depth.
- Bazel `toolchain.target_settings` semantics and platform-vs-flag caching were taken from rules_godot's existing usage, not re-verified in Bazel docs for this note.

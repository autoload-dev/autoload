## 1. Texture compression on the web: formats, options, imports, runtime selection, fallback

### Takeaway
A web export ships whichever VRAM-compressed variants the import produced *and* the preset's feature tags select: `for_desktop` adds S3TC/BPTC, `for_mobile` adds ETC2/ASTC, and the web exporter keeps all matching variants (no priority pruning), so enabling both roughly doubles VRAM-compressed texture payload. Desktop browsers almost universally expose S3TC/BPTC and almost never ETC/ASTC on Windows; mobile browsers are the reverse. A mobile browser given a desktop-only export falls back to CPU decompression to uncompressed RGBA, costing load time and 4-8x GPU memory for those textures. Two source-level hazards matter for Bazel: (a) without the project settings, which formats the importer produces depends on the **host CPU architecture of the import action** (ARM Linux/Windows hosts produce ETC2/ASTC only, x86 and all macOS hosts produce S3TC/BPTC only), and (b) the web exporter only validates the mobile case; a missing desktop import is not an export error in 4.7.2/4.8 beta.

### Cited Findings

**Export options and feature tags (web exporter)**
- `vram_texture_compression/for_desktop` (default `true`) adds feature tags `s3tc` and `bptc`; `vram_texture_compression/for_mobile` (default `false`) adds `etc2` and `astc`. The exporter also adds `threads`/`nothreads`, `web_extensions`/`web_noextensions` and `wasm32` — `G47 platform/web/export/export_plugin.cpp:348-367` (features), `:374-377` (option defaults). Platform features `web` plus the lowercased OS name `web` come from `platform/web/export/export_plugin.h:138-141`. This matches the prototype's recorded tags `web wasm32 nothreads web_noextensions s3tc bptc`. — local source
- Godot 4.8 beta has an identical `get_preset_features` (diffed) — `G48 platform/web/export/export_plugin.cpp:348-367`. — local source
- Export validation: `has_valid_project_configuration` sets `valid = false` when `for_mobile` is on and `ResourceImporterTextureSettings::should_import_etc2_astc()` is false. In 4.7.2 it does so **without any error message** (`err` stays empty) — `G47 platform/web/export/export_plugin.cpp:466-479`. In 4.8 beta it adds a message in command-line mode: "ETC2/ASTC texture compression is required for Web export ... enable 'Import ETC2 ASTC'" — `G48 platform/web/export/export_plugin.cpp:471-477`. — local source
- There is **no** web-exporter check for the desktop case (S3TC/BPTC missing). The only S3TC/BPTC check for arbitrary presets lives in the editor GUI export dialog (`editor/export/project_export.cpp:403-406`, `export_texture_format_error->show_for_texture_format(...)`), which does not run for headless `--export-*`. The macOS, Android and Apple-embedded exporters have their own checks (`platform/macos/export/export_plugin.cpp:2489,2495`, `platform/android/export/export_plugin.cpp:3148`, `editor/export/editor_export_platform_apple_embedded.cpp:2293`). — local source (grep of all `should_import_*` call sites in G47)
- Option comment in source: `for_mobile` is "ETC or ETC2, depending on renderer" (`export_plugin.cpp:377`); in Godot 4 it always maps to `etc2`/`astc` tags. — local source
- The docs say enabling both For Desktop and For Mobile gives "a bigger, but more compatible export" — [Exporting for the Web (4.7 docs)](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

**Project settings and the importer**
- `rendering/textures/vram_compression/import_s3tc_bptc` and `import_etc2_astc` are both defined with default `false` and are restart-required — `G47 servers/rendering/rendering_server.cpp:3659-3660`. — local source
- If the setting is false, the importer still imports a family when the **host OS** prefers it: `should_import_s3tc_bptc()` returns `OS::get_preferred_texture_format() == S3TC_BPTC`, `should_import_etc2_astc()` likewise for ETC2_ASTC — `G47 editor/import/resource_importer_texture_settings.cpp:38-53`. — local source
- The default `OS::get_preferred_texture_format()` is decided at compile time by CPU architecture: ARM (`__arm__`, `__aarch64__`, `_M_ARM64`) → ETC2_ASTC; x86/x86_64 → S3TC_BPTC — `G47 core/os/os.cpp:747-755`. macOS overrides it to S3TC_BPTC on all CPUs ("macOS supports both formats on ARM. Prefer S3TC/BPTC for better compatibility with x86 platforms") — `G47 platform/macos/os_macos.mm:1058-1062`. Linux has no override (only `core/os/os.cpp` and `os_macos.mm` define it, per grep of `core platform drivers`). — local source
- For `compress/mode = VRAM Compressed`, the importer writes one `.ctex` per enabled family: `<path>.s3tc.ctex` or `<path>.bptc.ctex` (BPTC when "high quality" or HDR) and `<path>.etc2.ctex` or `<path>.astc.ctex` (ASTC when high quality or HDR); it records each in `r_platform_variants` and the families in `formats_imported` metadata. The comment states the order: "Must import in desktop and mobile formats in order of priority, so platform chooses the best supported one (e.g. s3tc over etc2 on desktop)" — `G47 editor/import/resource_importer_texture.cpp:886-948`. The layered-texture importer uses the same two switches — `editor/import/resource_importer_layered_texture.cpp:513-514`. — local source
- Other compress modes (Lossless, Lossy, VRAM Uncompressed, Basis Universal) write a single `<path>.ctex` regardless of these settings — `G47 editor/import/resource_importer_texture.cpp:949-953`. — local source
- Default `compress/mode` is Lossless (0) for 2D textures and VRAM Compressed (2) for the 3D preset; layered textures default to Lossy (1) — `G47 editor/import/resource_importer_texture.cpp:232`, `resource_importer_layered_texture.cpp:144`. Textures detected as used in 3D are switched to VRAM Compressed or Basis Universal (per `detect_3d/compress_to`) with mipmaps on the next import — `resource_importer_texture.cpp:125-145`. — local source
- Godot's Android and iOS test fixtures, and several rules_godot fixtures, set `textures/vram_compression/import_etc2_astc=true` (e.g. `G47 platform/android/java/app/src/instrumented/assets/project.godot:30`; `rules_godot/godot/platforms/private/tests/library_composition/fixtures/*/project.godot:15`). rules_godot's import configuration keeps this setting (`rules_godot/godot/private/tests/project_config_test.py:476-515`). — local source

**What goes into the pack**
- On export, for each imported file the exporter keeps only `path.<feature>` remaps whose feature is in the preset's features and erases the rest ("Remove paths if feature not enabled"); if more than one remains, `resolve_platform_feature_priorities` may prune — `G47 editor/export/editor_export_platform.cpp:1641-1680`. — local source
- The web exporter's `resolve_platform_feature_priorities` is empty, so with both `for_desktop` and `for_mobile`, both the S3TC/BPTC and ETC2/ASTC `.ctex` go into the PCK — `G47 platform/web/export/export_plugin.h:143-144`. (By contrast, PC, Android, Apple-embedded and macOS exporters override it: `editor/export/editor_export_platform_pc.cpp:287`, `platform/android/export/export_plugin.cpp:4481`.) — local source

**Runtime selection on WebGL2**
- At load, `ResourceFormatImporter` walks `path.<feature>` keys in file order and takes the first whose feature `OS::has_feature` reports; if none is natively supported but one can be CPU-decompressed (`Image::can_decompress`), it uses the first decompressible one and logs "No natively supported texture format found for %s, using decompressable format %s" (verbose) — `G47 core/io/resource_importer.cpp:70-100`. — local source
- `has_feature("s3tc"/"bptc"/"astc"/"etc2")` is answered by the GLES3 driver config — `G47 drivers/gles3/storage/utilities.cpp:417-428`. On the web, Godot enumerates extensions via `emscripten_webgl_get_supported_extensions()` (because Emscripten ≥3.1.51 `glGetStringi` returns a fixed list) and inserts each name with and without a `GL_` prefix — `G47 drivers/gles3/storage/config.cpp:57-71`. — local source
- On GLES/WebGL (not desktop GL): `s3tc_supported` = `WEBGL_compressed_texture_s3tc` (or GL_EXT variants); `bptc_supported` = `GL_EXT_texture_compression_bptc`; `astc_supported` includes `WEBGL_compressed_texture_astc`; but **`etc2_supported = true` unconditionally** — `G47 drivers/gles3/storage/config.cpp:87-113`. — local source
- When a format is unsupported, the GLES3 texture upload sets `need_decompress = true` and decompresses on the CPU — `G47 drivers/gles3/storage/texture_storage.cpp:746-906`. The S3TC/BPTC decompressor (bcdec) is registered in all builds including templates — `G47 modules/bcdec/register_types.cpp:40-41`; `Image::can_decompress` checks those function pointers — `core/io/image.cpp:2932-2943`. — local source

**Basis Universal**
- Basis Universal is an importer compress mode (single `.ctex`) — `G47 editor/import/resource_importer_texture.cpp:232`. At load it is transcoded to a format chosen from `RS::has_os_feature("bptc"/"astc"/"rgtc"/"s3tc"/"etc2"/"astc_hdr")`, falling back to `RGBA32` — `G47 modules/basis_universal/image_compress_basisu.cpp:284-401`. The module builds on all platforms (`modules/basis_universal/config.py:1-4`). — local source

### Inferences
- **Host-dependent import outputs (Bazel risk).** With both settings `false` (the prototype's case: `import_etc2_astc=false`, and `import_s3tc_bptc` default false), the set of `.ctex` variants an import action writes depends on the Godot editor binary's CPU: Linux x86_64 or any macOS → `*.s3tc/bptc.ctex`; Linux arm64 (e.g. arm64 remote executors, Linux containers on Apple Silicon) → `*.etc2/astc.ctex`. The web pack exported from an arm64-Linux import with `for_desktop=true, for_mobile=false` would then drop all VRAM-compressed textures (no matching remap), and 4.7.2/4.8 beta report no error for that case. This follows from the cited code paths; it was not reproduced experimentally. Setting `import_s3tc_bptc=true` explicitly (or deriving it) removes the host dependence for the desktop family.
- **Per-target derivation is cheap in rules_godot's model.** Imports already run once per project and target platform, and the import configuration already carries `import_etc2_astc`. A rule-derived value per target platform (S3TC/BPTC for desktop-web, both for a "web_mobile" variant, ETC2/ASTC for Android/iOS) would not add a new cost class; it changes only the web target's import outputs. Conversely, leaving it to the project means a project that sets `import_etc2_astc=true` for Android also pays ETC2/ASTC encoding in its web imports, even if the web pack drops them.
- **Size.** Standard block-compression bit rates (DXT1/ETC2-RGB 4 bpp; DXT5/BPTC/ETC2-RGBA/ASTC 4x4 8 bpp) mean enabling both families roughly doubles VRAM-compressed texture bytes in the PCK and in the download; the web exporter does not prune either (cited above). Not measured on a project here.
- **Mobile browser with desktop-only export.** Android (S3TC ~31%) and iOS (~56%) browsers often lack S3TC/BPTC; Godot then decompresses S3TC/BPTC to uncompressed RGBA8 on the CPU in wasm at load time, raising GPU/wasm-heap memory for those textures by 4x (vs 8 bpp) to 8x (vs 4 bpp) and lengthening load. On memory-constrained mobile Safari this raises the risk of tab reloads (the 4.3 blog already notes a Safari reload over memory use).
- **Desktop browser with mobile-only export (Windows).** Because Godot sets `etc2_supported = true` unconditionally on WebGL2 while Windows browsers expose `WEBGL_compressed_texture_etc` only ~2% of the time, an ETC2-only pack on Windows would attempt native ETC2 uploads instead of CPU fallback; likely broken/black textures. Inference from source + survey data, not verified. A rules_godot design should therefore never produce a web pack without S3TC/BPTC unless explicitly mobile-only.
- **2D projects are mostly unaffected.** 2D textures default to Lossless (no VRAM variants), so the desktop/mobile question matters mainly for 3D projects or explicit VRAM-compressed textures. Basis Universal is the "one file, transcode at load" alternative that sidesteps the per-family duplication, at the cost of quality and transcode time.

### Gaps
- No measured PCK sizes for desktop-only vs both families on a real project; the prototype (Lichtpost) could measure this.
- Not verified experimentally what an ETC2 upload does on a Windows browser without `WEBGL_compressed_texture_etc`, nor the arm64-Linux import scenario.
- web3dsurvey dates/sample composition unknown; no better-dated public dataset found within the budget.

## 2. Renderers on the web: Compatibility only, `rendering_method.web`, WebGPU status

### Takeaway
Godot 4.7.2 and 4.8 beta run only the Compatibility renderer (OpenGL ES 3/WebGL 2) on the web. A Forward+ or Mobile project exports and runs on the web anyway, because the project setting `rendering/renderer/rendering_method.web` (only allowed value `gl_compatibility`) overrides the renderer via the `web` feature tag; the project just loses features unsupported by Compatibility. Official WebGPU support does not exist; the only WebGPU work found is an unaffiliated fork (2026).

### Cited Findings
- `rendering/renderer/rendering_method.web` is defined with hint `gl_compatibility` only and default `gl_compatibility`, commented "This is a bit of a hack until we have WebGPU support." — `G47 main/main.cpp:2649`; unchanged in `G48 main/main.cpp:2647`. The runtime reads `rendering/renderer/rendering_method`, which resolves feature overrides such as `.web` on a web build — `G47 main/main.cpp:2651-2655`. Web driver is `rendering/gl_compatibility/driver.web` = `opengl3` only — `main/main.cpp:2406`. — local source
- The web build disables Vulkan (`"vulkan": False` in `get_flags`) and links `-sMAX_WEBGL_VERSION=2` when `opengl3` is on; glslang (needed only for Vulkan/D3D12/Metal) is not built — `G47 platform/web/detect.py:83,256-266`; `modules/glslang/config.py:1-4`. — local source
- Docs (4.7): "Godot 4 can only target WebGL 2.0 (using the Compatibility rendering method)"; Forward+ and Mobile unsupported on web — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); renderer overview: Compatibility is "the only choice" on web — [Overview of renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
- Compatibility limits (4.7 docs): no compute shaders; no VoxelGI/SDFGI/SSIL; no volumetric fog or SSR; MSAA 3D/SSAA only (no TAA/FSR2/FXAA/SMAA); no decals, SSS, CompositorEffects, particle trails, HDR output; 8 omni + 8 spot lights per mesh; LightmapGI renders but baking needs RenderingDevice — [Overview of renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
- No WebGPU code in G48's `platform`, `drivers`, `servers` or `main` beyond the `main.cpp` comment (grep) — local source.
- An unofficial fork based on Godot 4.6.2 implements a WebGPU `RenderingDeviceDriver`; public beta May 10, 2026; claims ~80% of native Vulkan/Metal FPS and "up to 5x faster than WebGL" (README), while the GodotCon Boston 2026 talk abstract says ~4x; "not directly affiliated with or endorsed by the Godot Foundation" — [dwalter/godotwebgpu](https://github.com/dwalter/godotwebgpu); [GodotCon Boston 2026 talk](https://talks.godotengine.org/godotcon-boston-2026/talk/CT739D/). Claims are self-reported.
- Godot's 2023 slides noted its Vulkan/D3D12/Metal abstraction "doesn't fit WebGPU" (older source, 2023) — [W3C games CG slides, Fabio Alessandrelli](https://lists.w3.org/Archives/Public/www-archive/2023Dec/att-0001/gamescg-fabioalessandrelli-godot.pdf)
- Browser context: WebGPU now ships in Chrome, Firefox (Windows 2025-07, macOS Apple Silicon 2025-11) and Safari (2025-09) — per search summary of [Khronos WebGL/WebGPU SIGGRAPH 2026](https://www.khronos.org/developers/linkto/webgl-and-webgpu-sigg26) and [web.dev](https://web.dev/blog/webgpu-supported-major-browsers?hl=en) (not fetched in full).

### Inferences
- An analysis-time note for Forward+/Mobile projects (prototype decision 9) is accurate: such projects do not fail, they silently render with Compatibility. Shader and material imports are not renderer-specific in a way that changes the import outputs, so no extra web import variant is needed for the renderer (not verified per resource type).
- Because `rendering_method.web` has a single legal value, the ruleset has nothing to choose here until upstream WebGPU lands; a future WebGPU renderer would likely change templates (and possibly the feature/variant matrix), so web design should not hard-code "web == Compatibility" beyond diagnostics.

### Gaps
- No official Godot statement or roadmap date for WebGPU found for 2026; the GodotCon Boston 2026 talk content after July 2026 was not found.

## 3. Other web-platform limits relevant to design

### Takeaway
Web exports in 4.7.2/4.8 beta: no C#/.NET (hard export error, still in 4.8 beta), single-threaded by default with optional threads needing cross-origin isolation, sample-based Web Audio playback by default with effect limits, growable wasm32 memory starting at 32 MiB, `user://` on IndexedDB (not guaranteed persistent), no raw sockets (HTTP/WebSocket/WebRTC only), GDExtension only via the dlink templates with web-compiled side modules, Embree raycast and OpenXR not built, and Safari has extra WebGL2 issues.

### Cited Findings
- **C#/.NET**: with `MODULE_MONO_ENABLED`, the web exporter always fails: "Exporting to Web is currently not supported in Godot 4 when using C#/.NET. Use Godot 3 to target Web with C#/Mono instead." — `G47 platform/web/export/export_plugin.cpp:425-429`; same in `G48 platform/web/export/export_plugin.cpp:425-429`. — local source
- A prototype statically linking Mono into the web template was shown at GodotCon Boston 2025 (draft PR #106125), with limits (template/project must match threading, SIMD, exception handling and TargetFramework; invariant globalization only; ~72 MiB PCK for a simple prototype, ~23.8 MiB Brotli); "cannot commit to a specific timeline yet" (older source, May 2025) — [Godot blog, 9 May 2025](https://godotengine.org/article/live-from-godotcon-boston-web-dotnet-prototype/). Not merged as of 4.8 beta per the local source above.
- **Threads**: since 4.3 single-threaded is "the preferred and now default way"; threaded exports need `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, or the PWA service worker emulating them — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); motivation (COOP/COEP blocks cross-origin requests such as monetization/APIs, itch.io difficulties, Apple playback issues) — [Web Export in 4.3, 15 May 2024](https://godotengine.org/article/progress-report-web-export-in-4-3/) (older source). Threaded builds set `-sUSE_PTHREADS=1`, `PTHREAD_POOL_SIZE` from `Module['emscriptenPoolSize']||8`, `WASM_MEM_MAX=2048MB` — `G47 platform/web/detect.py:273-284`. `proxy_to_pthread` is off by default and forced off without threads or with dlink — `detect.py:59-63,286-297`. — local source
- **GDExtension**: requires `variant/extensions_support` (dlink template, `-sSIDE_MODULE=2`, `.dlink` suffix); extensions must be compiled specifically for the web — `G47 platform/web/detect.py:55-57,294-304`; [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html). Building templates requires Emscripten ≥ 4.0.0 — `detect.py:116-118`. — local source
- **Memory**: `INITIAL_MEMORY` default 32 MiB, `ALLOW_MEMORY_GROWTH=1`, stack 5120 KiB; arch `wasm32` (`-sMEMORY64=0`); size-optimized (`optimize=size`, "-Os reduces file size by around 5 MiB over -O3"); WASM SIMD on by default — `G47 platform/web/detect.py:41-64,83-93,162,307-317,332`. Embree raycast module disabled on web ("heavy and requires too much memory (GH-70621)") — `detect.py:84-85`. — local source
- **Modules not on web**: OpenXR builds only on linuxbsd/windows/android/macos — `G47 modules/openxr/config.py:1-6`; WebXR is web-only and incompatible with `proxy_to_pthread` — `modules/webxr/config.py:1-6`; camera module excludes web (`modules/camera/config.py`); `lightmapper_rd` and `betsy` are editor-only — local source. `javascript_eval` can be compiled out — `detect.py:53-54`.
- **Audio**: since 4.3 Web Audio sample playback is the default; no AudioEffects, reverb, doppler or procedural audio in that mode; switching `audio/general/default_playback_type.web` to Stream restores Godot's mixer at the cost of latency — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); [Web Export in 4.3](https://godotengine.org/article/progress-report-web-export-in-4-3/).
- **File system**: `user://` persistence needs IndexedDB ("allow cookies"), third-party cookies in iframes, and fails in private browsing; `OS.is_userfs_persistent()` "can give false positives" — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); implementation returns `idb_available` — `G47 platform/web/os_web.cpp:273-275`.
- **Networking**: "Low-level networking is not implemented due to lacking support in browsers"; HTTPClient/HTTPRequest (no chunked responses, same-origin policy/CORS), WebSocket client, WebRTC are available — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html). Web defines `UNIX_SOCKET_UNAVAILABLE` — `G47 platform/web/detect.py:256`.
- **Browsers**: "Safari has several issues with WebGL 2.0 support that other browsers don't have"; Chromium/Firefox recommended; single-threaded export "works very well on macOS and iOS too"; mobile works but native Android/iOS builds perform better — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html).
- **Serving**: `.wasm` must be served as `application/wasm`; server-side (Brotli) compression recommended for `.pck`/`.wasm`; itch.io is among hosts that "don't provide on-the-fly compression" — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html).

### Inferences
- C#/.NET can stay out of scope for web with no loss: upstream itself refuses the export in 4.7.2 and 4.8 beta. If upstream adds it, it will come as a different template family with extra matching constraints (threads, SIMD, TargetFramework), i.e. another axis in the template choice of prototype decision 1.
- Threads and dlink are the only template axes; memory, SIMD and `javascript_eval` are build-time template options, relevant only to source-built engines (which the prototype does not support on web yet).
- Pre-compression (`.br`/`.gz`) is valuable specifically for itch.io-like hosts; it is a pure packaging step and fits the ruleset's output-layout decision (prototype decision 6).

### Gaps
- No authoritative per-browser memory ceiling for mobile Safari found within budget.
- Did not verify whether 4.8 adds the built-in (pre)compression teased in the May 2025 article; not seen in the web exporter options diffed for features only.

## 4. Scope and usage: how common web exports are and what pipelines automate

### Takeaway
Web is a major Godot target for jams and itch.io: itch.io lists ~157k browser-playable games tagged made-with-Godot out of ~174k Godot games (snapshot 2026-11-23), and Godot reached 47% of GMTK Game Jam 2026 entries. Existing CI prior art (godot-ci Docker image, firebelley/godot-export) only wraps headless `--export` of presets and adds deployment (GitHub/GitLab Pages, itch.io via butler); none handles texture-format or COOP/COEP concerns.

### Cited Findings

### Inferences
- Typical user needs from a web pipeline: one directory/ZIP with `index.html` uploadable to itch.io (single-threaded, no COOP/COEP), static hosting (GitHub Pages, which cannot set COOP/COEP headers, so threads need the PWA service worker), optional PWA, a custom HTML shell, and pre-compressed assets. The prototype's `index.*` directory + ZIP already meets the itch.io/static-host case.
- Prior art treats texture formats as "whatever `export_presets.cfg` and `project.godot` say" and runs imports on whatever runner host it uses; rules_godot would be the first to make the import-format choice explicit/hermetic, which is a differentiator given the host-architecture dependence found in section 1.
- Given that ~90% of itch.io Godot titles are browser-playable, web support is likely high-value for jam/indie users of a Godot ruleset, but less so for the ruleset's current mobile-app users (Android/iOS), whose apps use native extensions and add-ons that the web cannot run without an Emscripten toolchain (prototype decision 2).

# Glossary

The terms this repository uses in code, documentation, commits, reviews and conversation.
Each term has one meaning. Where a familiar Bazel or Godot term means something narrower
here, its row says so. The "In code" column names the identifiers that carry the term; its
paths are relative to `rules_godot/` unless they name repository tooling (`tools/ci/`,
`tools/conventions/`, `tools/addons/`) or `addons/`.

## Naming rules

- Use the term this page gives for a concept, and no synonym. Write English technical terms
  untranslated, also in conversations held in another language: rule, target, action,
  provider, toolchain, exec group, extension library.
- Name a rules_godot provider value after its term: `pack`, `extension`, `project`,
  `resources`, `runtime`, `desktop_app`, never `info` or `*_info`. A File inside it takes a
  qualifier, such as `pack_file` or `runtime_executable`; a list takes the plural or its
  role, such as `dependencies` or `importers`.
- When a provider or rule has two fields or attributes of the same kind, qualify both,
  unless their difference is obvious: `runtime_resource_paths` and `editor_resource_paths`,
  `member_resource_paths` and `import_resource_paths`.
- `runtime_` qualifies what the runtime loads, `editor_` what the editor loads. `target` is
  only the Bazel term; it never names the runtime side.
- `native` means compiled code (C, C++, Objective-C, Swift, Java through JNI) and its
  libraries, and Bazel's `native.*` module in Starlark. Every other sense has its own term:
  an extension, extension library or platform library for what an extension or add-on
  brings, "Bazel's built-in" for Bazel's own rules, [evaluated](#ruleset-internals) for what
  Bazel reports after loading and analysis, and shell for the application around the
  engine.
- `platform` alone is Godot's operating system, used only in the engine configuration (see
  [platform (Godot)](#platforms-and-operating-systems)); a Bazel platform is always
  qualified. In platform library, platform resources and `platform_deps`, platform means
  Android or Apple.
- Tests, test files and fixtures are named by the verification architecture's
  [naming](verification-architecture.md#naming) rules.
- Write terms out in names: `operating_system`, `operating_systems`, `cpu`, `cpus`; never
  `os`, `oses`, `arch` or `architecture`.
- Names in upstream terms keep them, although they break a rule above: Bazel's and Godot's
  own names, such as `@platforms//os`, SCons's `arch=` and the export options
  `binary_format/architecture` and `architectures/*`; `build_target` of
  `godot_engine_build` and `--build-target` of
  `tools/engine/configure.py`, after SCons's `target=`;
  `godot_app.ios_minimum_os_version`, after rules_apple's `minimum_os_version`; the export
  platforms `ios_sim_arm64` and `ios_sim_x86_64`, after apple_support's platforms; `binary`
  for an executable, as in `godot_editor_archive.binary` and its repository's `:binary`,
  `prebuilt_editor.binary`, `prebuilt_runtime.binary` and
  `godot_engines.binaries.editor_binaries`, after Godot's release archives, while prose says
  editor or runtime executable; `<name>.native_apk` and
  `<name>.native_bundle`, rules_android's outputs.

## Platforms and operating systems

| Term | Meaning | Not to be confused with | In code |
|---|---|---|---|
| host | The machine Bazel runs on, such as your Mac. `bazel run` starts its binary here, so an editor started with `bazel run` runs on the host (exec group `run`). | The execution platform, which differs from the host when actions run remotely; the editor platform (`editor_*`); the shell (`shell_*`). | `@platforms//host`, `HOST_CONSTRAINTS` |
| execution platform | The Bazel platform build actions run on. Locally it is the host; with remote execution, such as BuildBuddy, it is the platform of the remote executors, often Linux. Tests run on the execution platform of their test action. "Remote executor" names only a machine of a remote execution service. | The host; the target platform. | `cfg = "exec"`, `--extra_execution_platforms` |
| target platform | The Bazel platform a build produces outputs for, selected with `--platforms`. | A Bazel target, which is a buildable label. | `--platforms` |
| platform (Godot) | Godot's name for an operating system it builds and exports for, as in export templates per platform and SCons's `platform=`. rules_godot uses it in the engine configuration: the components, recipes and prebuilt archives that declare the editor and the runtime. | A Bazel platform, which this glossary always qualifies: target, execution, export or editor platform, or platform slice. Outside the engine configuration, say operating system. | `platform` of `godot_editor_component`, `godot_runtime_component`, `godot_engine_build`, `prebuilt_runtime`, `GodotComponentInfo`, `GodotRuntimeInfo`, `GodotEngineVersionInfo`; Godot's export preset platform name, such as `Linux` or `iOS`, is `preset_platform` |
| operating system | The operating system a pack, application or extension library is for: `linux`, `macos`, `android` or `ios`. In the engine configuration it is called platform, as Godot does. | A Bazel platform, which also fixes the CPU and other constraints. | `operating_system` fields of `GodotPackInfo` and `GodotDesktopAppInfo` (an extension's libraries name theirs in their feature tags); `godot_export_platform.operating_system` |
| CPU | The instruction set something is built for, Bazel's `@platforms//cpu`. Public attributes take the constraint label, such as `@platforms//cpu:armv7`; internally rules_godot names it by Godot's CPU tag, such as `arm32`. Godot calls it architecture. | An Android ABI, such as `arm64-v8a`, which names a CPU in Android's terms; Bazel's `--cpu` values such as `ios_sim_arm64`, which also encode an Apple environment. | `cpu` and `cpus` fields and attributes |
| CPU table | The one mapping from each `@platforms//cpu` value Godot can express to its Godot CPU tag, bitness, Android ABI and Apple split CPU per iOS environment. | Godot's CPU feature tags themselves; the Android ABI options of the engine profile, which list what Godot's exporter offers. | `CPU_TABLE`, `cpu_tag()` in `godot/private/config/settings.bzl` |
| environment (iOS) | `device` or `simulator`: the Apple environment of an iOS export platform and its platform slices. | An Android SDK or Apple SDK installation; the Apple build platform a Mach-O file records, such as `ios_simulator`, which code calls `sdk`. | `//godot/private/config:environment`, `GodotPackInfo.environment`, `godot_export_platform.environment` |
| editor variant | The variant `editor`: a `godot_app` runs its start pack's project from sources with the editor executable instead of exporting it, on a Linux or macOS target platform. The tool configuration is the editor variant too. | The editor platform, which an editor executable is built for; the editor toolchain; the `editor_runtime` feature tag, which any editor running a project has. | `//godot:editor`, `godot_source_application` in `godot/private/run.bzl`, `tools/platforms/launch/launch_editor.py` |
| export platform | A target platform declared with `godot_export_platform`: an operating system, a set of CPUs and, for iOS, device or Simulator. Selecting it with `--platforms` builds a pack or an application for every CPU in the set. | Godot's export platform, which is only the operating system. | `godot_export_platform` in `godot/platforms/defs.bzl` |
| platform slice | The part of an export platform that builds for one CPU, and for iOS one of device or Simulator. Each is a target platform of its own; `godot_export_platform` declares one for each CPU, and iOS environment, beside the export platform. A desktop export platform is its own single platform slice. A multi-CPU application combines its platform slices. Never just "slice". | A slice inside an XCFramework or a universal Mach-O file, which is one prebuilt binary. | `//godot/private/config:platform_slices`, `PLATFORM_SLICES`, `<name>.platform_slice_<cpu>` targets, `platform_slice_transition` |
| child platform | A Bazel `platform()` whose `parents` is an export platform, its parent platform. It adds constraints, flags and execution properties, and keeps the export platform's operating system, CPUs and platform slices. | A platform slice, which the export platform declares itself. | `consumer_child` in `godot/private/config/tests` |
| variant | `release`, `debug` or `editor`: which of Godot's binaries a build is for, as Godot's own build target (`template_release`, `template_debug`, `editor`). `release` and `debug` are the export templates: they select the runtime, the export's `debug`/`release` feature tags and the source-built extension libraries. `editor` is the editor variant. A runtime component has one of the two template variants; an editor component has none. | C++ optimization (`--compilation_mode`), which is set independently; the role, which says what an engine component is. | `--@autoload_rules_godot//godot:variant`; `variant` of `godot_runtime_component`, `prebuilt_runtime`, `GodotComponentInfo`, `GodotRuntimeInfo`, `GodotPackInfo`, `GodotEngineVersionInfo` |
| feature tags | Godot's names for properties of a running engine, such as `linux`, `arm64`, `debug`, `editor`, `editor_runtime` (an editor running the project), `template` and `simulator`. A GDExtension descriptor lists each library under a set of feature tags; rules_godot derives the set from the configuration that built the library. | Bazel features (`features = [...]`), which configure rules_cc toolchains. | keys of `[libraries]` in a `.gdextension` file; `GodotExtensionInfo.library.tags` |
| reserved feature tags | The feature tags a platform slice fixes: operating system, CPU, variant, and device or Simulator. Custom features cannot claim them, so they cannot change which configured extension library Godot loads. | Custom features. | `_RESERVED_FEATURE_TAGS` in `godot/private/config/settings.bzl` |
| custom features | The feature tags the build settings a project names give in a configuration: a string setting its value, a boolean setting its own name when true. Packs export with them and source runs start with them; the build's own Godot processes never have them. They take no part in choosing an extension library. | Reserved feature tags; Bazel features. | `godot_project.custom_features`, `GodotProjectInfo.custom_features` |
| tool configuration | The build configuration in which Godot runs as a build tool: imports, initialization, exports, the editor. An extension provides a library for it through its tool view; its feature tags end in `editor`. | The `editor` purpose of a view; the editor variant of a `godot_app`, which runs the project on the target platform. | `//godot:tool`, `//godot/private/config:tool`, `tool_transition`, `<name>.tool` |

## Engine

| Term | Meaning | Not to be confused with | In code |
|---|---|---|---|
| editor | The Godot editor executable. rules_godot uses it in build actions to import, initialize and export projects, to start the game from a project's files in source runs and tests, and to open the Godot editor UI for `godot_editor`. | The editor view, which is the directory the editor UI opens. | `//godot:editor_toolchain_type` |
| runtime | The engine an application ships: Godot's export template for one platform slice and variant. | The `runtime` purpose, which also covers source runs with the editor. | `//godot:runtime_toolchain_type`, `GodotRuntimeInfo`; `runtime` parameters and `<name>.godot_runtime` of the Android and iOS application backends; `engine` names checks of engine files of either role, such as `check_engine` and mnemonic `GodotEngineVersion` |
| role | Whether an engine is the editor or the runtime. | The variant, which a build has. | `role` of `GodotComponentInfo` and `GodotEngineVersionInfo` |
| component | The declaration of the editor or the runtime for one slot: its payload and its toolchain registration. | A Godot scene component or an add-on; resources. | `godot_editor_component`, `godot_runtime_component`, `GodotComponentInfo` |
| provenance | Where a component's payload comes from: its kind, version, origin, digest and customizations, carried on the resolved toolchain for diagnostics. | Bazel's build provenance; where a runtime's facts come from, which is `facts_source`; the owner of a resource path. | `GodotComponentInfo`, `ToolchainInfo.godot.provenance` |
| slot | One combination of role, platform and CPU, plus, for runtimes, the iOS environment and the variant. Of the components of the selected engine registered for a slot, the first one wins. | A platform slice, which is part of what one build produces. | toolchain registration order, `--extra_toolchains` |
| engine name | The name that keeps an engine apart: a component that has one fills slots only for targets that select it, with their `engine` attribute or a build's `--@autoload_rules_godot//godot:engine`. `godot_engines.engine` registers an engine under its name, which also names its hub and prefixes its other repositories. The default engine serves targets while neither names one: the engine registered with `default = True`, whose components also answer to its name, and components without a name. | The Godot version. | `--@autoload_rules_godot//godot:engine`, `//godot:default_engine`; `engine` of the operations and `godot_app`, of `godot_editor_component`, `godot_runtime_component`, the `godot_engines` tags and `GodotComponentInfo`; `name` and `default` of `godot_engines.engine`; `default_engine` of the components and `<name>.default_engine`; `engine_transition` |
| registration set | A package of components registered together through its `:all` target. The first set registered for a slot wins; a root module's own sets and `--extra_toolchains` come before the engines' toolchains. | An engine, which declares recipes and a hub. | `@<name>//toolchains:all`, `@godot_engines_toolchains//:all`, consumer packages such as `//engines/custom:all` |
| hub | The repository `@<name>` that `godot_engines` generates for each engine. Its `toolchains` package declares one component per valid slot; `@<name>//toolchains:all` registers that engine alone. The extension also generates `@godot_engines_toolchains` with the toolchains of every registered engine's components, which rules_godot's own module registers, so consumers register no engine toolchains. | A registration set of your own. | `godot/engine/private/hub.bzl`, `@godot_engines_toolchains` |
| payload | The engine files a component declares: an editor executable, or a runtime's executable or libraries with the files it needs beside them. | Extension libraries, which belong to an extension. | `GodotRuntimeInfo.files`, `bundle_files`, `ToolchainInfo.godot.payload` |
| editor platform | The operating system and CPU an editor executable is built for; an engine provides one editor per editor platform. A build can use an editor on an execution platform or the host with that operating system and CPU. | The export platform. | `EDITOR_PLATFORMS` in `godot/engine/private/catalogue.bzl` |
| prebuilt engine, source-built engine | A prebuilt engine comes from Godot's release archives or another pinned archive of executables and templates; a source-built engine is compiled by a source recipe. One engine can have both, slot by slot. | The official engine, which is one kind of prebuilt engine. | `godot_engines.binaries`; `GodotComponentInfo.kind` (`prebuilt` or `source`); `GodotRuntimeInfo.facts_source` |
| official engine | A prebuilt engine from Godot's own releases: the editors and export templates Godot publishes for a version, which the catalogue pins for each catalogued version of `godot_engines.engine`. The `official` and `beta-official` bazelrc configs select platform slices it covers. | A prebuilt engine from another pinned archive; a source-built engine. | `godot/engine/private/catalogue.bzl`; bazelrc configs `official`, `beta-official`; `--kind official` and `--engine-aar` of the beta validations |
| source recipe | One engine build from pinned Godot sources with your modules and patches, for one row. | A prebuilt engine downloaded from Godot's releases. | `godot_engine_build` |
| engine tree | One engine's Godot sources, extracted once with its build policy's patches applied and its files made read-only; every source recipe and the Android shell library of the engine link its files hard into their own repositories instead of extracting the sources again. | The source archive, `@<name>_source`, which the tree and recipe pins extract; a recipe's repository, which holds what it generates. | `godot_engine_tree`, `@<name>_tree`, `tree.json`, `tools/engine/tree.py` |
| build policy | The modules, patches and options every source recipe of an engine shares: its `build` tag's, with an `editor` tag's modules and options for its editor recipes, or, without a `build` tag, those of Godot's official builds. Slots with different policies need separate engines. | A source recipe, which builds one row; a build profile, which one application's runtime applies. | `godot_engines.build`, `godot_engines.editor` |
| build profile | Godot's `.gdbuild` file: classes to leave out of the engine (`disabled_classes`) and build options (`disabled_build_options`). Only applications have one: it reduces that application's runtime only. Its classes reach the recipe's class generator as an input; its build options shape a source recipe's graph and pin, so a profile with build options must be registered, which gives the engine's runtime recipes a runtime variant. | Bazel's `--profile`; a purpose of a Godot process. | `build_profile` of `godot_app`; `godot_engines.runtime_profile`; `//godot/private:build_profile`, `:build_profile_label`; `untuned_only` of `godot_runtime_component`; `tools/engine/build_profile.py` |
| runtime variant | A source recipe's graph configured with the build options of a registered build profile, declared in the recipe's repository beside the recipe's own graph. Targets the two declare alike keep one label; differing attributes select on the application's build profile, and a lock file pins each variant beside its recipe. | The variant `release` or `debug` of a runtime; a separate engine. | `runtime_profiles` of `godot_engine_build`; `tools/engine/variants.py`; the lock file's `variants` table; `@<recipe>//:pin_variant_<n>` |
| runtime profile | What an application's runtime leaves out as Godot's detection finds it in the project: one build profile (`.gdbuild`) of classes and build options, derived by running the selected engine's editor headless and kept in the checkout. Classes the engine needs whatever the project names are removed from the detection. | Godot's detection output itself; the engine's recipe. | `godot_runtime_profile`; `godot/private/runtime_profile.bzl`; `tools/runtime_profile.py` |
| recipe pin, lock file | A source recipe's pin is its configured build graph with the digest of what that graph depends on; an engine's lock file holds the pins of its recipes. With a lock file no host configures a recipe, and `bazel run @<name>//:pin` rewrites it by configuring each recipe on an execution platform Godot accepts; `:pin_<platform>` rewrites one platform's pins and keeps the others. | Bazel's `MODULE.bazel.lock`; a Maven lock file such as `maven_install.json`. | `lock_file` of `godot_engines.engine`, `@<recipe>//:pin`, `@<name>//:pin`, `@<name>//:pin_<platform>`, `@<name>//:pinned`, which fails while a recipe has no current pin, `tools/engine/pin.py`, mnemonic `GodotPinRecipe` |
| row | One valid combination of platform, CPU, iOS environment and build target; an engine that builds from source declares one source recipe per row, `@<name>_<row>`, except for editors its binaries cover. | A slot, which a row's recipe fills. | `godot/engine/private/source_build_rows.bzl` |
| engine library, engine AAR | The engine compiled as a library: Android's `libgodot_android.so` and iOS's static library. On Android an application packages it inside the engine AAR: the Android shell library with the slot's engine library. | Extension libraries; the Android shell library as Godot ships it. | `godot_android_runtime.engine_library`, `@<recipe>//:engine_library`, `<name>.engine_aar` |
| shell | The native application code around the engine. On Android it is Godot's Java/Kotlin library (an AAR), the Android shell library; on every operating system it includes the shell files and shell assets an application rule writes. | The host; a command shell such as `sh`. | `godot_android_shell`, `godot_android_runtime.shell`, `godot_engines.binaries.android_shell_urls` |
| shell files, shell assets | What application rules write for the shell from what Godot decides for the export: manifests, themes, `Info.plist` files and Android's command line file `assets/_cl_` (shell files), and icons and splash images (shell assets). | Files of the project. | `godot/platforms/private/shell.bzl`, `godot/private/shell_assets.bzl`, `tools/platforms/godot_shell.py`, mnemonics `GodotShellFile`, `GodotShellAssets` |
| shell default, override | A shell file or shell asset is a shell default for its slot; an application's own file for the same slot is an override. The override reaches rules_android or rules_apple unchanged, and the shell leaves its default out. Slots are an Android resource's type, name and configuration qualifiers, the main manifest, a top-level `Info.plist` key, the app icons, the launch screen and the privacy manifest. | A patch of the shell file; an export option. | `godot_app.android_manifest`, `ios_infoplists`, `ios_app_icons`, `ios_launch_storyboard`, `platform_resources`; `tools/platforms/shell_overrides.py`, mnemonic `GodotShellYield` |
| template activity | Godot's `com.godot.game.GodotApp`, the activity of Godot's Android Gradle template. An Android application runs the copy of its Godot minor unchanged. | Godot's `GodotActivity` base class in the Android shell library; a shell file. | `template_activity` of the engine profile, `godot/private/engine/android/` |

## Projects and resources

| Term | Meaning | Not to be confused with | In code |
|---|---|---|---|
| resource path | Where a file appears inside the Godot project: its project-relative path without the `res://` prefix, such as `levels/one.tscn`. A string with the prefix is a `res://` path. | A workspace or execroot path. | `godot_extension.resource_path`; `godot_resources.resource_paths`, which maps labels to resource paths, the direction you author |
| `*_resource_paths` | A dict of resource paths to Files: which file appears where in the project. | A list of paths, which is `*_paths`. | `GodotViewInfo.member_resource_paths` and similar fields; `GodotViewInfo.editor_resource_paths`, every file the editor stages; lists such as `packed_paths` of an export report; the manifest keys `extension_resource_paths` and `extension_library_paths`, the runtime side of all extensions of a run or a pack |
| resources | A `godot_resources` target: files with their resource paths, the resources they depend on and the add-ons their files use. It imports its own files under the project of the operation that reaches it. | Godot's `Resource` class; a project or an add-on. | `godot_resources`, `GodotResourcesInfo` |
| add-on | A directory of a Godot project declared once with its parts: a runtime part, an editor part with its roles, extensions, platform libraries, Info.plist fragments, autoloads, settings and the add-ons it needs. Every file lives below its directory, by default `res://addons/<name>/`. An extension by itself is an add-on of only that extension. | Resources, which declare no contributions; Godot's editor plugin, which is only the editor part. | `godot_addon`, `GodotAddonInfo`; `extension_addon` in `godot/private/addon.bzl` |
| runtime part, editor part | The two file sets of an add-on. The runtime part's files are members of every operation containing the add-on and import as one unit. The editor part, the `plugin.cfg` and the files its editor plugin loads, is a tool: only the Godot processes of its roles stage it, and no pack, source run or application contains it. | A member, which is content; an import input. | `godot_addon.srcs` and `editor_srcs`; `GodotAddonInfo.runtime_files` and `editor_files` |
| role | What an add-on's editor part does for a build: an importer, which the processes converting files of its suffixes stage, and editor tooling, which every editor view loads. No build runs an add-on's export plugin. | A purpose, which is a kind of Godot process. | `godot_addon.importer_suffixes`, `GodotAddonInfo.importer_suffixes` |
| use | The declaration that the files of resources use an add-on: the add-on in their `deps`. Every operation containing those resources contains the add-on and those it needs; no file of the add-on becomes an input of their import. | A dependency on other resources, which imports first. | `GodotResourcesInfo.addons`, `classify` in `godot/private/resources.bzl` |
| named add-on | An add-on a project lists in its `deps`, because no content uses it, such as an editor-only add-on. Every operation of the project contains it; its parts import under the project like those of a used add-on. | A used add-on. | `godot_project.deps`, `GodotProjectInfo.named_addons`, `<project>.named_addons` |
| contribution | An autoload, setting or Info.plist fragment an add-on or a project declares. An operation merges autoloads and settings in the add-ons' dependency order, the project's last; an application merges the Info.plist fragments of the add-ons of its packs with its own. | A pack's own `settings`, which set one export. | `GodotAddonInfo.autoloads`, `settings`, `platform_contributions`; `_resolve` in `godot/private/view.bzl` |
| member | A file that belongs to an operation's content through its selection: scripts, scenes, assets and data. An export contains every member it packs, a script or scene as it is and an importable asset as its import result. | An import input. | `GodotViewInfo.member_resource_paths`, `member_owners` |
| import input | A file that only the import of another file reads, such as the `.bin` buffer of a glTF model. No export contains it, in any form. | A member. | `godot_resources.import_inputs`, `import_resource_paths`, `import_owners` |
| Godot-ignored file | A file Godot's editor file system never scans: below a directory that holds a `.gdignore` or a `project.godot` (`EditorFileSystem::_should_skip_directory`, which also skips the project data directory `.godot`), or hidden, its name or a directory's beginning with a dot (`EditorFileSystem::_scan_new_dir`, `DirAccessUnix::is_hidden`; Godot 4.7.2). Godot never imports or registers it and writes no sidecar for it, while code reads it through `FileAccess` when Godot runs from the sources. Source runs, tests and editors stage it; exports leave out its directory, though Godot's include filter packs a hidden file of a visible directory. A pack's reference to a file it leaves out is an `ignored_reference` error, and a warning for a `FileAccess` read, which a `runtime_references` entry from the reading file acknowledges. | A member, which an export contains; an import input, which only imports read. | `GodotResourcesInfo.ignored_resource_paths`, decided by `godot_ignored` in `godot/private/paths.bzl`; `tools/godot_files.py`, whose `hidden_by` names what hides a file from the export; `select_pack` in `tools/pack_selection.py` |
| composition | What a `godot_resources` target or a view merges from its own files and its dependencies: members, import inputs and their owners; a view also the runtime parts and extensions of its add-ons. | An editor view, which is a directory on disk. | `compose` in `godot/private/resources.bzl` |
| import unit | The files of one `godot_resources` target that Godot imports together in one action with one cache entry. A target without files of its own has no import unit. | A Bazel package. | `GodotResourcesInfo.units` |
| unit heads | The import units a `godot_resources` target stands for when another unit depends on it: its own unit, or, for a target without files of its own, the units its dependencies stand for. A dependent unit imports after these. | All units in the closure. | `GodotResourcesInfo.unit_heads` |
| owner | The label string of the target that declared a resource path, used in diagnostics, like Bazel's `File.owner`. | Provenance, where an engine component's payload comes from. | `member_owners`, `import_owners`; `owner` of units, settings, autoloads and relationships |
| project, project context | A `godot_project` target: the configuration of a product, its authored `project.godot` with settings, autoloads, main scene, context files, and the add-ons it names. It holds no resources. Every operation names one project, and resources import under the project of the operation that reaches them, once per project and target platform. | A Godot project directory on disk; a project directory under `{examples,tests}/projects/`; a view, which holds files. | `godot_project`, `GodotProjectInfo`, the setting `//godot/private:project` in `godot/private/context.bzl` |
| operation | A target that runs Godot or reads files under a project: `godot_pack`, `godot_run` and `godot_test` without a `pack`, autoload_gdunit's `gdunit_test`, `godot_editor`, `godot_metadata_sync`, `godot_runtime_profile` and `godot_resource_graph`. Each names one project and its own selection. | A Bazel action; an application, which takes a pack. | the macros in `godot/private/pack.bzl`, `run.bzl`, `editor.bzl`, `analysis.bzl`; `declare_view` in `godot/private/view.bzl` |

## Progress messages

An action's `progress_message` is one verb from this table, then `%{label}`: Bazel prints
it on its status line, and a long label already fills one. The verbs are gerunds, as in
rules_cc, rules_java, rules_android and rules_apple (`Linking %{output}`, `Building %{output}`,
`Validating %{label}`, `Bundling %{label}`). The mnemonic names the action's kind in
`--subcommands`, the execution log and BuildBuddy, so the message neither repeats it nor
says what the action reads.

| Verb | Actions | Mnemonics, for example |
|---|---|---|
| Importing | The editor converts a unit's assets. | `GodotImport` |
| Initializing | The editor derives a view's script-class and UID caches. | `GodotInitialize` |
| Exporting | The editor exports, or the writer writes, a pack's PCK or its configuration. | `GodotPack`, `GodotPackConfiguration`, `GodotPackWrite` |
| Probing | The editor reports facts Godot decides. | `GodotImportableSuffixes`, `GodotShellAssets` |
| Validating | A check whose product is its pass or fail: scripts and scenes, resource references, metadata, flags, export options, the engine version, Maven minimums. | `GodotValidate`, `GodotResourceGraphCheck` |
| Generating | A build tool derives files from its inputs: configuration, class fragments, unit interfaces, metadata, the resource graph, pack selection and descriptors, shell files, engine sources, bindings, an icon, a `.dSYM`. | `GodotProjectConfig`, `GodotMetadata`, `GodotShellFile` |
| Bundling | Files are put into an archive or a bundle. | `GodotDesktopPackage`, `GodotDebugSymbols` |
| Stripping | Native code loses its symbols. | `GodotStrip` |
| Signing | A bundle is code signed. | `GodotMacosSign` |

An output name in parentheses follows the label where one target runs the same verb for
outputs that vary with its content or configuration: a unit (`Importing <unit label>`), a
shell file (`Generating %{label} (Info.plist)`), a configuration purpose, a kind of metadata
check, a binary's `.dSYM`. Fixed stages of one rule share a verb and a label.

A new action takes a verb of the table, or extends the table with the action's row.

| test kind | One of the eight categories of ruleset test that the [verification architecture](verification-architecture.md#test-kinds) defines, each with a location, a form, allowed dependencies and the claims it may make. | A verification kind of the [verification policy](verification.md#verification-kinds), which names the evidence a check supplies; a test tag. | none |
| altitude | How much of the build a test observes, from one rule's analysis up to a running application. The [test kinds](verification-architecture.md#test-kinds) are ordered by it, and a behavior is tested at the lowest altitude that observes its failure. | Test size or duration. | none |
| Starlark unit test | A [test kind](verification-architecture.md#starlark-unit-test) for pure Starlark logic, written with rules_testing `unit_test` in a `tests` subpackage of the ruleset. | An analysis test, which needs a rule's analysis. | none |
| analysis test | A [test kind](verification-architecture.md#analysis-test) that asserts providers, actions and analysis errors of ruleset targets, written with rules_testing `analysis_test` in a `tests` subpackage. | A build-output test, which inspects what actions produce. | skylib `analysistest` in existing tests |
| build-tool unit test | A [test kind](verification-architecture.md#build-tool-unit-test): a `py_test` of a build tool's library on given inputs, without a Godot binary. | A repository-tooling test, which tests a tool that does not run in builds. | `tools/<area>/tests/` |
| build-output test | A [test kind](verification-architecture.md#build-output-test) that inspects the real outputs of fixture targets in one configuration, including determinism. | A run test, which executes the output; artifact inspection in a consumer scenario. | none |
| run test | A [test kind](verification-architecture.md#run-test) that runs Godot or an exported desktop application on ruleset fixtures. | Mobile runtime acceptance, which needs a device. | `godot_test`, GdUnit suites |
| consumer scenario | A [test kind](verification-architecture.md#consumer-scenario): a package of `e2e/rules_godot/` in the root module that shows, with the public API only, what a user can build, inspect and run. | A regression project, which predates the verification architecture; an example. | none |
| example test | A [test kind](verification-architecture.md#example-test): an example's tests for its own behavior. | Ruleset coverage, which examples do not provide. | `examples/**/tests/` |
| repository-tooling test | A [test kind](verification-architecture.md#repository-tooling-test): a Python test of a tool that serves the repository, such as a check, a CI script or a setup tool, beside that tool. | A build-tool unit test, which tests a tool that runs in builds. | `tools/conventions/**/*_test.py`, `tools/ci/*_test.py` |
| add-on unit test | A test of an add-on module's code with its language's test tool, such as `cc_test` or `py_test`, without a Godot project, beside the unit in the module ([add-on module tests](verification-architecture.md#add-on-module-tests)). | An add-on end-to-end test, which runs Godot. | `addons/<module>/**/tests/` |
| add-on end-to-end test | A test that uses an add-on as an application does, by running Godot or building a project, in the root module's `e2e/addons/<module>/` ([no-godot-in-addon-modules](conventions.md#no-godot-in-addon-modules)). | A consumer scenario, which tests the ruleset; a demo test. | `e2e/addons/<module>/` |
| demo test | A test of an add-on module's example application itself, in `examples/addons/<module>/tests/`. | An add-on end-to-end test, which tests the add-on. | `examples/addons/<module>/tests/` |
| registry test module | The consumer module in `bcr/<name>/` of a released module that the Bazel Central Registry builds from the release archive ([registry-test-module-in-bcr](conventions.md#registry-test-module-in-bcr)). | A consumer scenario of the root module. | `<module>/bcr/smoke/`, `registry_test_modules` in `tools/setup/modules.py` |
| artifact test rule | A test rule of the root module that inspects a built App Bundle or iOS application without running it; the consumer scenarios, the examples and the ruleset's tests use it ([artifact test rules](verification-architecture.md#artifact-test-rules)). | An API of the ruleset; a test operation such as `godot_test`, which runs Godot. | `android_bundle_test` and `ios_app_test` in `tools/artifact_tests/` |
| host job | One of the two jobs of `.github/workflows/ci.yml`, `linux` and `macos`, each run as `aspect ci <host>`. A host job selects the tests of both workspaces that its `ci-<host>` config allows by tag, and on Linux runs the checks first. CI requires both on every run; the Source engine workflow runs the source-built engine tests on its own. The pre-push hook runs the checks and the `fast` tier instead. | A Bazel platform; a workflow job in general; a host, the machine Bazel runs on. | `_ci_steps` in `.aspect/develop.axl`, the configs `ci-linux` and `ci-macos` in `shared.bazelrc` |
| test tag | A tag of a test target that selects it by machine or cost: `godot_process` (it starts a Godot process, RG026), `source_engine` (it builds an engine from source), `android` and `ios` (it needs that mobile operating system's toolchains, such as the scenarios' mobile smoke tests and the `<name>.build_test` of a release), `engine_pins` (the engine pins' check, the same on every host, which only the Linux job runs). The tiers `fast` and `all` and the host jobs' configs filter on them; a test without a platform tag runs on both hosts. | A `.bazelrc` configuration, which filters by tag; a [test kind](verification-architecture.md#test-kinds). | `--test_tag_filters` of the `fast`, `all`, `ci-linux` and `ci-macos` configs in `shared.bazelrc`, `release_test` in `examples/releases.bzl` |
| work | One named piece of verification that is no single Bazel command: shell commands in one module directory, which may need the Android environment or its own variables, such as `conventions`, `addon-template` or `source-engine:full`. The host jobs and the Git hooks' tasks run work by name; `aspect work <name>` runs it locally, and `aspect work` lists it. A piece that is one Bazel command is documented as that command. | A Bazel target, which work runs; an Aspect CLI task. | `Work` and `WORK` in `tools/ci/work.py` |

## Terms to avoid

| Instead of | Say | Why |
|---|---|---|
| runtime extension library, editor extension library | extension runtime library, extension editor library | the extension comes first and its role follows, as the engine's roles are editor and runtime |
| GDExtension library | extension library | Godot's documentation says it; GDExtension stays for titles and Godot's concept |
| lane (for a CI job or a set of tests) | host job; test tag | CI selects tests by tag and runs one job per host; no lane mechanism remains |
| source engine (outside the Source engine workflow) | source-built engine | the workflow name invites the short form |
| runner, test runner (for a test target or test adapter) | test target; test adapter | runner means the build tool a launcher starts |
| composed project, project members (of a pack, run, test or check) | view; the operation's members | a project holds no resources; each operation's view combines it with its own selection |
| pack selection (for `packing`) | packing | selection is an operation's `deps`; packing decides what of it a pack contains |
